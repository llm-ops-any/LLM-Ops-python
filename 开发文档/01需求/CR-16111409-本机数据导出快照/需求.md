## 1. 用户原话（一字不改）

> 本机的sql数据导出一份放到postgres

## 2. 目标

1. **把本机现有业务数据变成一份可恢复的文件**：当前数据只在 `docker/volumes/db/data`（Docker 数据卷目录）里，
   换机器 / 重装 / 误删即全丢，没有任何可读的备份。
2. **放到 postgres 的初始化目录**（`docker/postgres/`，已挂载为容器内 `/docker-entrypoint-initdb.d`）：
   空数据卷首次启动时自动灌入，做到「拷仓库 + 起容器 = 数据回来」。
3. **快照与迁移兼容**：保留 `alembic_version`，让 api 启动时的 `db upgrade` 只补后续迁移，不重复建表。

## 3. 范围

### 3.1 做

- `pg_dump` 导出 `llmops` 库 → `docker/postgres/llmops_data.sql`（`--no-owner --no-privileges --encoding=UTF8`）。
- 文件名刻意排在 `init.sql` **之后**（`i` < `l`）：initdb 按字典序执行，扩展必须先于业务表建好。
- `.gitignore` 增加排除项：快照含真实账号邮箱、密码 hash、`api_key` 密文，**不进版本库**。
- 用临时库 `llmops_verify` 真实恢复一次，比对关键表行数，验证 dump 可用后删库。

### 3.2 不做

- **不动现有数据卷**（`docker/volumes/db/data` 只读使用，不删、不重建）。
- **不把快照应用回现有库**（现有库已有数据，再灌会冲突；本 CR 只产出快照）。
- 不含 Redis / Weaviate 数据（向量与缓存不在 SQL 里，`dataset` 的向量需重建，见风险 R-03）。
- 不启 api / ui / nginx（导出只需 db，其他服务保持 Exited）。
- 不改 `docker-compose.yaml`、`init.sql` 任何一行。

## 4. 验收标准

| 编号 | 标准 |
|---|---|
| AC-01 | 产出 `docker/postgres/llmops_data.sql`，由 `pg_dump` 生成、UTF-8 编码、行数与体积可核对 |
| AC-02 | 快照与源库一致：`account` / `app` / `workflow` / `dataset` / `message` / `api_key` 六表行数与源库相同 |
| AC-03 | **恢复可用**：导入临时库 `llmops_verify` 无致命错误，`alembic_version = 9c4e2a1b7d30`，六表行数与源库一致 |
| AC-04 | 快照不含 `OWNER TO` / `GRANT` 语句（`--no-owner --no-privileges`），换机恢复不依赖角色 |
| AC-05 | 现有数据卷未被修改：`volumes/db/data` 内容与操作前一致，源库行数不变 |
| AC-06 | `.gitignore` 已排除快照文件，`git status` 不出现该文件 |
| AC-07 | 快照在 initdb 目录内**排在 `init.sql` 之后**，空卷首次启动能正确执行（扩展先建、表后建） |
| AC-08 | 文档留痕：`开发文档/00规则/部署规范.md` 第六节补「把现有数据带到新环境」的做法 |
