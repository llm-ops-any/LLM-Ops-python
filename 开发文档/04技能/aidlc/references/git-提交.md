# git 提交规范

> 本文件是 `SKILL.md` §F 的展开：**判据留在 §F，这里放格式细则、例外与反例**。
> 2026-11-04 定：**scope 强制写 CR 号**；一次提交只装**同一条 CR** 的文档与代码。
> 起因：三个项目各写一份「七、提交」，细节各异；发射场近 200 条提交里带 CR 号的 **0 条**。
> 规范不在一个地方，AI 就按各自项目的那份走，换项目换规矩。

## 1. 一句话格式

```
<type>(CR-<8位号>): <中文摘要>
```

例：`feat(CR-16102901): 头部下拉改用 tippy 实现`

## 2. type 只用这七个

| type | 用于 | 对应 CR 类型 |
|---|---|---|
| `feat` | 用户能感知的新行为 | `01需求/` |
| `fix` | 修缺陷、报错、数据不对 | `02缺陷/` |
| `refactor` | 只改内部实现，行为不变 | `03技术债/` |
| `docs` | 只动文档（CR 文档、`00规则`） | 任意 |
| `perf` | 性能优化（**得先有数字**） | 任意 |
| `chore` | 版本号、依赖、构建配置、`.gitignore` | 任意 |
| `revert` | 回滚 | 任意 |

**type 和 CR 类型对不上就是错**：`01需求/` 里的 CR 用 `fix` 提交，等于把"新功能"记成了"修 bug"。

## 3. scope = CR 号，强制

- **8 位数字**，取自目录名 `CR-<8位号>-<简称>/` 的前半，写成 `CR-16102901`
- 不是 8 位的都不合规：`CR-3`、`cr-16102901`（小写）、`16102901`（缺前缀）都不行
- 这一条是硬要求：**没有 CR 号的提交 = 这次改动没有留痕**，事后只能翻 diff 猜为什么改

## 4. 一个提交只装一条 CR

提交内容 = **这条 CR 的文档**（`开发文档/<类型目录>/CR-<8位号>-<简称>/` 下的一切）
＋ **这条 CR 改动的代码文件**。

- ❌ 两条 CR 混一个提交
- ❌ 把"顺手改的"夹带进来 —— 顺手改的也要开 CR（技术债），否则就留着别提交
- ✅ 文档和代码可以分两次提，但**两次都用同一个 CR 号**

## 5. 例外（只有这四种）

| 情况 | 写法 | 要求 |
|---|---|---|
| 仓库杂务且确实不值一条 CR（`.gitignore`、README、依赖升级、版本号） | `chore(repo): 中文摘要` | 正文写**为什么不开 CR** |
| **技能副本同步**（只改 `开发文档/04技能/aidlc/`） | `chore(aidlc): 中文摘要` | 正文写**改了技能的哪几处、同步到哪些项目** |
| 合并提交 | 保持 git 默认的 `Merge branch ...` | 不套格式，不改文案 |
| 回滚 | `revert(CR-<号>): 回滚 <原摘要>` | 正文写回滚原因 |
| 紧急热修 | 仍要开 CR，先 `fix(CR-<号>): ...` | 事后补 CR 文档，不许"先上线再补流程" |

`(repo)` 与 `(aidlc)` 是**仅有的两个**非 CR scope。别造 `(init)`、`(misc)`、`(other)`。

> **为什么技能同步单独一个 scope**：技能改动跨项目、没有单条 CR —— 同一份补丁要落到 6~7 个仓库，
> 给每个仓库开一条 CR 等于同一件事记六七遍。但也不能混进 `(repo)`（那是仓库杂务，技能是基础设施），
> 所以单独留 `(aidlc)`；它的提交只允许出现在 `开发文档/04技能/aidlc/` 这一个目录里。

## 6. 正文写三件事

标题一行说完，正文按需写（没有的不硬凑）：

1. **改了什么** —— 一句话，比标题具体
2. **已知缺口** —— 没跑的测试、没验证的场景、留的坑（`仅静态` 档位必须写「未做自动化测试」）
3. **关联** —— 设计文档路径、外部 issue

## 7. 不提交的东西

`开发文档/_汇总/`（整目录）、`dist/`、`node_modules/`、`*.log`、临时截图、`.env` 本地覆盖、任何含密钥的文件。

生成物过期时先跑 `python 开发文档/04技能/aidlc/scripts/汇总.py --check`，它会告诉你哪个视图该重生成。

## 8. 提交前四步

1. `git status` 看一遍：**只有本 CR 的文件**
2. 生成物是不是最新的（`汇总.py --check`）
3. `git add` **逐个文件或目录** —— **禁止 `git add -A` / `git add .`**（会把别人的改动一起端走）
4. 分支 `agent/<智能体名>/<功能简述>`（见 `协作规范.md`），提交后推送

## 9. AI 提交用谁的身份

- **用配置好的 git 身份**：`git config user.email` 必须是 `00规则/团队配置.md` 里登记过的人。
  `audit-signature` 扩展取的就是它，**签谁的名就是谁负责**。
- **不加 AI 署名**（不写 `Co-Authored-By: Claude`）：署名会把责任稀释成"机器干的"，
  而审计要的是"这件事由谁批、谁担"。
- 想留痕就写在正文：`由 <agent 名> 在 CR-<号> 下执行`。

## 10. 反例

| 反例 | 错在哪 |
|---|---|
| `feat: 修复下拉框` | 没有 scope；而且 `fix` 写成 `feat` |
| `feat(CR-16102901): 改下拉框，顺便调了打包配置` | 两件事挤一个提交 |
| `update` / `修改` / `1` | 事后完全无法检索 |
| `feat(CR-3): ...` | CR 号不是 8 位（opcapp 的规范里曾这么写，示例本身就是错的） |
| `git add -A && git commit -m "..."` | 把别人的未提交改动一起端走 |
| `chore(misc): 杂项` | `(misc)` 不在例外清单里；要么归到某条 CR，要么用 `(repo)` |
| 照着 `git log` 最近几条的风格写 | 历史风格不是格式来源，缺 CR 号的旧提交是**反例**不是惯例（见 §12） |

## 11. 项目可以加严，不能放松

各项目 `00规则/开发规范.md` 的「七、提交」**可以加**项目特有要求（例如必须先跑某个检查、
分支命名带业务前缀），但**格式这一条不能改**：`<type>(CR-<8位号>): <中文摘要>` 是全局约定，
改了就回到"每个项目一套"的老路。

## 12. 历史提交不是格式依据

`git log` 看到的是「过去怎么写」，不是「应该怎么写」。**格式只认 §1**，历史一律不作依据。

- **历史合规率普遍很低，照抄＝照错抄**。实测 opcapp：763 条提交里仅 **32 条带 CR 号（4%）**，
  最近 50 条有 **36 条连 `type` 都没有（72%）**。看最近 10 条定风格，等于照着那 72% 写。
- **宿主内置的 `/commit` 命令会自动注入历史**：它的模板里写着 `Recent commits: !git log --oneline -10`，
  一执行就凭空多出 10 条历史风格进入上下文。**那 10 条不作为依据**，只用来避开"这条分支最近在干什么"。
- **判断依据只有两个**：§1 的格式，§5 的四类例外。type 拿不准就查 §2 的对照表，
  不要去翻历史找"上次类似改动怎么写的"。
- **项目特有的加严规则优先于历史**，但不得放松 §1（见 §11）。

> 已知的项目级坑：opcapp 的 AIDLC 锚点写在 `CLAUDE.md`（`AGENTS.md` 是它 fork 上游那份，**没有**提交格式），
> 且 `开发文档/` 被 `.gitignore` 整目录排除 —— 在该项目提交时，若只读了 `AGENTS.md` 或没加载本技能，
> 上下文里就只剩"历史风格"，必然写错。**先确认 `CLAUDE.md` 的 AIDLC 段在，再提交。**
