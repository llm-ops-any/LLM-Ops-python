# CR-16102809 决策记录

## D-01 缓存放 `storage/tts_cache/`，不放 Redis / 数据库 / COS

| 方案 | 问题 |
|---|---|
| Redis | 音频大（1 分钟约 2.6MB PCM），挤占 Redis 内存，且本项目 Redis 是 Celery broker + 队列，不该塞大对象 |
| PostgreSQL | 用 `text` 存 base64 会让表迅速膨胀，且备份变慢 |
| COS | 需要外网与鉴权，多一次往返；当前单机部署收益不足 |
| **文件系统（选中）** | `storage/` 已挂载到宿主机且可写，零依赖，读写是本地 IO |

- **理由**：这是「一次合成、多次回放」的静态资源，天然适合文件。
- **代价**：多机部署时缓存不共享。当前单机，不构成问题；将来上多机再换 COS。

## D-02 缓存 key 必须带「引擎 + 音色 + 模型 + 文本指纹」

```text
storage/tts_cache/<message_id>__<engine>__<sha1(voice|model)>__<sha1(answer)>.json
```

- **理由**：`CR-16102803` 支持三档引擎切换。用户从 `dashscope` 切到 `omni`、或换音色后，**必须重新合成**，否则会播错声音。
- **为什么还要文本指纹**：`message_id` 理论上对应固定 `answer`，但消息可能被"重新生成"。带指纹可以天然失效，不用额外处理。
- **被否**：只用 `message_id` 做 key —— 换音色后会播旧声音，是很明显的 bug。

## D-03 只缓存**完整**合成结果

- **做法**：在生成器正常跑到 `for ... in provider.tts_stream()` 结束后才落盘。
- **理由**：用户中途关页面时生成器被丢弃（`GeneratorExit`），此时已收到的音频是半截，缓存下来会播放到一半突然结束。
- **实现要点**：落盘代码放在 `try` 的 `else` 分支或循环正常结束后，**不能**放 `finally`。

## D-04 TTL 7 天 + 单文件上限 20MB

| 参数 | 值 | 理由 |
|---|---|---|
| TTL | 7 天 | 语音合成结果不会变（同引擎同音色），但模型版本可能升级；7 天内重复听的概率最高，之后清了也无所谓 |
| 单文件上限 | 20MB | 约对应 7~8 分钟音频；超过通常意味着异常长文本，缓存它性价比低 |
| 清理时机 | **读取时惰性清理** | 不引入定时任务；每次访问顺手判断过期就删，实现最简 |

- **被否**：加 Celery 定时清理。为了一个缓存目录引入定时任务，运维面变大而收益很小。
- **代价**：长期没人访问的过期文件会留在盘上。可在构建说明里给一条手工清理命令兜底。

## D-05 命中缓存时仍按 SSE 逐块发送

- **做法**：缓存里存的是 chunk 列表，命中后逐块 `yield` 同样的事件，最后发 `tts_end`。
- **理由**：前端逻辑完全不用动（仍是 `tts_message` 累加 → `tts_end` 结束）。若改成一次性发完，前端可能依赖分块节奏做进度显示。
- **代价**：多几十次 `yield`，本地循环开销可忽略。

## D-06 缓存文件名不含用户 id，靠目录权限与随机 UUID 保证不可枚举

- **理由**：`message_id` 是 UUID，无法猜测；且接口本身已校验 `created_by`，缓存文件不直接对外暴露路径。
- **被否**：把缓存目录挂到 nginx 静态路径 —— 那会绕过鉴权，**绝对不能做**。
