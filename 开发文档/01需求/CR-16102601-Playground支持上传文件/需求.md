## 1. 用户原话（一字不改）

> Playground中用户提问部分可以上传文件

## 2. 目标

1. **Playground 里能传文件**：在「用户提问」输入框下方添加附件（图片 / 文档），随提问一起发给应用。
2. **不是前端假动作**：`POST /openapi/chat` 真正接受 `files` 并把内容交给模型；第三方按同一契约也能传。
3. **与现有附件链路一致**：数量上限、单文件上限、文本截断、图片走 URL、落库格式全部复用已有实现与常量，**不另造一套**。

## 3. 已确认的澄清（2026-10-26，张勇答复）

| # | 问题 | 结论 |
|---|---|---|
| Q1 | 做到哪一层 | **开放 API 正式支持**：`/openapi/chat` 的 `files` 是对外契约，回写 `api/docs/01.项目API文档.md` |
| Q2 | 允许传哪些文件 | **图片 + 文本类文档**：图片走对象存储 URL（视觉模型看图）；pdf/word/txt/md/csv/xlsx 解析正文进上下文 |
| Q3 | 输入区形态 | **保持表单**：在「用户提问」下方加「添加附件」+ 已选文件 chip，不改成聊天式输入条 |
| Q4 | 是否落库 | **落库并回显**：写 `Message.attachments`。**现实约束**：Playground 右侧只有响应面板、没有历史消息列表 ⇒ 详见 §4.2「不做」第 1 条 |

## 4. 范围

### 4.1 做

- Playground 输入区：添加附件、已选列表（名称/大小/类型）、逐个删除、上传中状态、失败提示
- 前端本地预检：单次 ≤5 个、单文件 ≤30MB，超限不发请求
- 请求体 `files` 字段：`[{name, extension, size, mime, kind, text?, url?}]`，无附件时**完全不出现该字段**
- 等价 curl 带上 `files`，可直接复制执行
- 后端 `OpenAPIChatReq` 加 `files` + 复用 `ChatAttachmentsMixin` 校验
- 后端注入上下文：复用 `build_query_with_attachments`（单附件 ≤8000 字符、总量 ≤20000 字符）
- 落库：`Message.attachments = build_attachment_metadata(files)`
- 回写 `api/docs/01.项目API文档.md`（`/openapi/chat` 的 `files` 字段、结构、上限、示例）

### 4.2 不做（明确排除）

| 不做 | 理由 |
|---|---|
| Playground 历史消息列表 / 会话回显 UI | 现状右侧只有「回答 / 事件流 / curl」，没有消息列表；加列表是另一个页面级改造。**「回显」落地为：已选附件 chip 在发送后保留 + 附件元信息落库可查**；历史轮次模型也看不到上轮附件正文（与主页调试一致，附件只参与当轮调用） |
| 开放 API 提供 multipart 上传接口 | 附件契约是「前端上传解析后回传 `name` + `text`/`url`」；第三方自备正文或可访问 URL 即可，不需要新增鉴权体系里的上传端点 |
| 把主页 `ChatInputBar` 换到 Playground | 用户选 A（保持表单，改动最小）；换输入条会牵动整页布局与端点驱动的表单结构 |
| 语音输入、附件预览大图、下载按钮 | 不在本次诉求内 |
| 改主页 / WebApp / 辅助 Agent 的附件链路 | 已跑通，本次只接第四个入口 |
| 数据库迁移 | `message.attachments`（JSONB）已存在，无需 alembic |

## 5. 功能需求

### FR-01 输入区添加附件

在「用户提问」字段下方新增附件区：一个「添加附件」按钮（支持多选）＋ 已选文件 chip 列表。

- 每个 chip 显示：文件名、大小（KB/MB）、类型标识（图片 / 文档 / 文件）、删除按钮
- 上传中的 chip 显示 loading，不可删除；上传失败给出中文原因并允许重试
- 已有的表单字段、端点切换、发送/停止逻辑不变

- **AC-01** Playground「Chat 对话」端点下，「用户提问」下方出现「添加附件」按钮；选 2 个文件后出现 2 个 chip，可逐个删除。
- **AC-02** 选第 6 个文件时前端拦下并提示「单次最多携带 5 个附件」；选 >30MB 文件提示「单个附件不能超过 30MB」；两种情况都不发请求。
- **AC-03** 上传失败（如后端 500 / COS 不可用）时 chip 标红并给出中文原因，不阻塞发送其它内容。

### FR-02 请求体传递 files

`buildRequest()` 把附件数组放进 body 的 `files`；无附件时该字段不出现（保持旧请求字节级兼容）。

- **AC-04** 加 1 个 txt + 1 张 png 后发送，抓包/后端日志可见 body 含 `files`，两项分别为 `kind=text`（有 `text`）与 `kind=image`（有 `url`）。
- **AC-05** 不加附件发送，body 字段与改造前完全一致（`app_id`/`query`/`stream`/`conversation_id`/`end_user_id`，无 `files`）。

### FR-03 等价 curl 带附件

右侧「等价 curl」包含 `files` 全文，可原样粘贴执行。

- **AC-06** 面板 curl 含 `"files": [...]`；复制出来的命令能直接跑通（含附件）。

### FR-04 后端接受并校验 files

`OpenAPIChatReq` 增加 `files = ListField("files", default=[])`，并混入 `ChatAttachmentsMixin`。

- **AC-07** 传 `files` 不是数组 → 400，`code=validate_error`，中文原因。
- **AC-08** 传 6 个附件 → 400，原因含「最多携带5个附件」。
- **AC-09** 附件缺 `name`，或 `text` 与 `url` 都为空 → 400，原因分别为「附件名称不能为空」「附件内容不能为空」。
- **AC-10** 不传 `files` 的老请求 200，行为与改造前一致（回归）。

### FR-05 附件内容进入模型上下文

复用 `build_query_with_attachments(query, attachments)` 构造 `HumanMessage`：有 `text` 注入正文，无 `text` 有 `url` 注入文件地址段。

> **链路现实（2026-10-26 实测确认）**：该函数对没有 `text` 的附件只拼一段中文纯文本
> （`【附件信息】文件名 / 文件类型 / 文件地址`），**不构造多模态 `image_url` 内容块**，
> 图片像素从不进入模型。三个既有入口（应用调试 / WebApp / 辅助 Agent）行为完全一致。

- **AC-11** 上传一份内容含唯一暗号（如 `ZQ-7788`）的 txt，问「文件里的暗号是什么」，回答包含 `ZQ-7788`。
- **AC-12** 单附件正文 >8000 字符时被截断（响应/日志可见截断标记），请求不 500。
- **AC-13**（2026-10-26 按 `决策记录.md` **D7** 降级）传 png 时附件以 `kind=image` + 对象存储 `url`
  **正确进入上下文段**、请求 200 不报错；**不要求视觉模型看懂图片**——当前链路只把地址当文本传给模型，
  API 文档需同步注明「当前不解析图片内容」。

### FR-06 附件元信息落库

创建 `Message` 时写 `attachments=build_attachment_metadata(files)`。

- **AC-14** 查库 `select attachments from message where id=...`：非空数组，含 `name`/`kind`/`url`（图片）或 `text`（文本类，≤4000 字符）与 `truncated` 标记。
- **AC-15** 落库后 `message.query` 仍为**原始提问**（不含附件正文），与既有调试链路一致。

### FR-07 接口契约回写

- **AC-16** `api/docs/01.项目API文档.md` 的 `/openapi/chat` 章节含 `files` 字段说明：结构、`kind` 三种取值、上限（5 个 / 30MB / 文本 100000 字符）、示例请求、无附件时省略该字段。
