## D-01 三档并存可切换，而不是只选一个引擎

- **背景**：PO 明确「做一个配置项，可以切换…这样我能测试这三种方式的效果」。
- **决策**：`engine` 一个字段切三档（`browser` / `omni` / `dashscope`），三套实现同时存在。
- **被否**：只实现最优一档（省一半代码）。否掉理由：PO 要横向对比听感与延迟，删掉的正是他要测的。
- **代价**：后端多约 120 行 provider 代码；前端播放器要同时支持 `SpeechSynthesis` 与 PCM 流。
- **决策人**：PO（需求原话）+ DEV（实现形态）。

## D-02 浏览器档作为默认值

- **理由**：① PO 原话「优先使用浏览器的语音、播放功能」；② 零成本、零网络、不落库；③ 没有 Key 也能先跑通闭环。
- **代价**：Chrome 的 Web Speech API 依赖 Google 服务，大陆网络下常 `network` 报错（现有代码已有该错误分支，说明踩过）。故它只是「默认」，不是「唯一」。
- **决策人**：PO。

## D-03 不引 `websockets`，用已装的 `websocket-client`

- **背景**：参考实现 `omni_spoken_assistant.py` 用的是异步 `websockets`，镜像里没有。
- **决策**：用同步 `websocket-client==1.8.0`。
- **理由**：① `开发规范.md` §八.1 不新增依赖；② 本项目接口是同步 Flask + SSE 生成器，同步 WS 天然贴合，异步库还要在同步 worker 里跑事件循环，反而多一层麻烦。
- **被否**：加 `websockets` 进 `requirements.in` 重编（属技术债 CR，不该在本功能里夹带）。
- **决策人**：DEV。

## D-04 配置存 `platform_setting` KV，不建新表

- **决策**：`name=speech_provider`，`value` 存 JSON（Key 用 `lib/secret.encrypt_secret` 加密）。
- **理由**：① 沿用 `CR-16102600` 大模型设置（`name=model_provider`）已验证的套路：加密 + 掩码 + 5 秒 TTL 缓存 + 环境变量兜底；② **无迁移**，回滚成本为零。
- **代价**：配置项无强类型校验，靠 schema 兜。
- **决策人**：DEV。

## D-05 音频统一「PCM base64 over SSE」，不转码不落盘

- **背景**：Omni 输出 `pcm/24000/16bit/mono`；CosyVoice 默认输出 mp3，可指定 PCM。原项目前端用 `MediaSource + audio/mpeg` 播 mp3。
- **决策**：两档服务端都输出 **PCM base64**，复用既有 SSE 事件名（`tts_message` / `tts_end`），前端用 Web Audio API 播 PCM。
- **理由**：① 镜像里没有 ffmpeg，服务端转 mp3 不可行；② PCM 直传省一次编码、延迟最低；③ 前端 Web Audio 播 PCM 比 `MediaSource` 兼容性更好（Safari 也能播）。
- **代价**：原项目的 `useAudioPlayer` **不能照抄**，必须重写（已计入工作量）。
- **决策人**：DEV。

## D-06 默认 `cosyvoice-v3-flash`，而不是需求原话的 `v3.5-flash`

- **证据**：`前置资源.md` P-04 —— v3.5-flash 四个音色 + 换专属域名，**均 0 字节静默失败**（`Engine return error code: 418`）；v3-flash 立即成功。
- **决策**：默认值用 `cosyvoice-v3-flash` + `longxiaochun_v3`，但**模型名做成配置项**，PO 账号若开通 v3.5 改配置即用，不用改代码。
- **为什么不报错给用户看**：SDK 把失败吞成 0 字节，会表现为「静音」，故 provider 里必须判 `len(audio)==0` 并抛业务错误，否则用户点播放没声音也不知道为什么。
- **决策人**：DEV（与需求原话偏差，已写入 `需求.md` 与验收报告，请 PO 过目）。

## D-07 TTS 懒加载：点播放才建连接

- **理由**：PO 原话「需要启动TTS的时候再启动」。Omni 是长连接、按 token 计费，空闲保活纯烧钱。
- **实现**：每次播放请求建一次 WS（请求级生命周期），流结束即关；不建连接池、不做常驻会话。
- **代价**：每次点播放多一次 WS 握手（实测首包 0.51 秒，其中握手占一部分）。若 PO 反馈"点下去要等"，再议连接复用（属新 CR）。
- **决策人**：PO（原话）+ DEV（实现）。

## D-08 服务端 ASR 只随 `dashscope` 档提供

- **理由**：PO 要求浏览器优先；`omni` 档本身也能做 ASR（`input_audio_transcription` 配 `qwen3-asr-flash-realtime`），但那需要上行音频流，属"实时对话"形态，不在本 CR。
- **代价**：`omni` 档目前只有 TTS，没有 ASR。若 PO 想测 Omni 的识别能力，需另开 CR。
- **决策人**：DEV。

## D-11 Omni 朗读用「强指令 + 朗读稿包装 + 响应级指令」三重约束

- **触发**：实现后自测发现 omni 档把「今天的天气很好，我们出去走走吧。」当成对话**回应**了
  （转录成 `好啊，今天天气确实不错……你想去哪儿？`），即风险 R-05 真实发生。
- **实测**（`证据/前置实测-5`）：温和指令 2/2 跑偏；强指令 + `【朗读稿】` 包装 2/2 通过；
  强指令 + `response.create.instructions` 2/2 通过。
- **决策**：三重约束同时上（session instructions + 输入包装 + response 级 instructions）；
  比对朗读忠实度前先剥掉 `【朗读稿】` 标签。
- **被否**：① 只靠温和指令 —— 实测不可靠；② 检测到跑偏就自动重试 —— 每重试一次多一次计费，
  且失败是语义层面的，重试收益低，改为**只记 warning 不重试**。
- **代价**：强指令措辞不能软化，后续改文案时要保留否定句式（"绝对不能回应"）。
- **决策人**：DEV（依据实测）。

## D-12 服务端 ASR 只接受 WAV，前端必须自己打包 WAV

- **事实**：`paraformer-realtime-v2` 只吃裸 PCM 帧 + `format=wav`；实测把 **webm 容器**丢给它直接解析失败
  （`前置实测-3` 里 `fun-asr` 报 `failed to parse webm file`）。
- **而**：浏览器 `MediaRecorder` 在 Chrome 上只能产 `audio/webm;codecs=opus`，拿不到 wav。
- **决策**：前端录音用 **Web Audio API 采集 PCM → 自行封装 16k/16bit/单声道 WAV → 上传**。
  零依赖（不引 `js-audio-recorder`，符合 `开发规范.md` §八.1），且采样率可控。
- **被否**：① 服务端转码 —— 镜像里没有 ffmpeg；② 让用户改浏览器设置 —— 不可控。
- **代价**：前端录音多约 60 行（AudioWorklet/ScriptProcessor + WAV 头拼装）。
- **决策人**：DEV。

## D-10 CosyVoice 档保留，不因「控制台搜不到」删档

- **触发**：PO 2026-10-28 反馈「阿里百炼上搜不到 cosyvoice 相关模型，是不是给错了」。
- **证据**：闭环验证通过 —— 合成返回 50664 字节真 mp3（`ID3` + `QTSSE` 头），ASR 转回文本与原文**完全一致**（`03-前置资源.md` P-04 附）。
- **决策**：判定口径为 **API 实测可用**，不以控制台可见性为准；CosyVoice 档保留。
- **理由**：控制台可见性与 API 可用性是两件事 —— 业务空间隔离、无在线体验入口都会造成「能调但看不到」。
- **被否**：因搜不到就砍掉 `dashscope` 档。否掉理由：PO 明确要对比三种效果，砍了就没得比；且实测可用，砍掉是浪费已验证的能力。
- **若后续 PO 环境确认该账号确实无 CosyVoice 授权**：改配置切 `cosyvoice-v2` 或退化为只留 `omni` 档，代码不动。
- **决策人**：DEV（依据实测），结论待 PO 复认。
