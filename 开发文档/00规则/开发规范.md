# 开发规范

- 生效：2026-10-26
- 适用：本项目的全部代码与测试
- 性质：**项目级约定**。与 AIDLC 技能里的流程规则冲突时，流程以技能为准，代码风格以本文件为准。

> **怎么用**：已按本项目实际情况填掉带尖括号的地方，其余条目**保留**——它们是踩过坑才写下来的，删之前先确认本项目确实不需要。
>
> **写法原则：每条都写「为什么」。** 没有理由的规矩，下一个人遇到例外时没法判断该不该破。

---

## 一、语言与运行环境

| 规则 | 为什么 |
|---|---|
| **Python 3.10**（`api/requirements.txt` 由 `pip-compile` with Python 3.10 生成）；不用 3.10 之后的语法（如 3.12 的泛型参数语法 `def f[T]()`） | 镜像基础环境是 3.10；升版本要让全仓依赖一起重编 |
| **前端 Vue 3 + TypeScript + Vite**；依赖版本以 `ui/package.json` 锁定为准，不升「最新」 | 与既有 87 个 `.vue` 写法一致；升级要单独走 CR |
| **交付形态：Docker Compose 起 7 个容器，对外入口统一走 nginx:80** | 端口、反代、健康检查都在 `docker/docker-compose.yaml` 里定死了 |
| 格式：后端沿用仓内现有风格（4 空格缩进）；前端走 `npm run lint`（eslint）与 `npm run format`（prettier） | 避免整文件格式化产生巨型 diff |

> **不引外部依赖**（新 pip 包 / npm 包 / CDN / 字体 / 图标库）—— 要引先走技术债 CR，不在功能迭代里顺手加。
> `api/requirements.txt` 是 `pip-compile` 的生成物，**手改会被下次编译覆盖**；要加依赖改 `requirements.in` 后重编。

## 二、代码结构

- **后端四层**：`api/app/http/`（入口 `app.py` + DI 容器 `module.py`）→ `api/internal/router|handler`（路由与视图）→ `api/internal/service`（业务逻辑，主要写这里）→ `api/internal/core`（Agent / 模型 / 工具 / 工作流 / 检索能力）。
  - 视图只做参数校验与响应组装，业务写 `service/`，跨模块能力写 `core/`。
- **前端分层**：`ui/src/{views,components,stores,services,hooks,models,utils}`；页面在 `views/`（约 74 个组件），通用组件在 `components/`，请求统一走 `services/`，状态在 `stores/`（pinia）。
- **持久化单一出口**：数据库只经 SQLAlchemy 模型 + service；**表结构变更必须走 alembic 迁移**（`api/internal/migration/`），不许手改库。
- **模型与工具的注册走 YAML**（`api/internal/core/language_model/providers/**/*.yaml`、`api/internal/core/tools/**`），不在 Python 里硬编码模型名 —— 本项目全部模型能力走统一中转平台，硬编码的官方模型名在平台上不存在。
- **渲染只读 / 动作集中派发**：前端不在组件模板里直接改 store 内部状态。

## 三、命名

| 对象 | 规则 |
|---|---|
| 文档、目录 | 中文（代码文件名除外，按语言惯例） |
| 后端标识符 | 英文 snake_case（类名 PascalCase） |
| 前端标识符 | 英文，小驼峰；组件文件 PascalCase；组合式函数 `useXxx` |
| 函数 | 动词开头（`get_xxx` / `build_xxx` / `parse_xxx`） |
| 布尔 | `is` / `has` / `can` 开头 |
| 常量 | 全大写 + 下划线 |
| 测试挂点 | `data-testid`，kebab-case，**是契约不是装饰** |

**新增交互元素必须带 `data-testid`**，否则那段交互永远进不了自动化。

## 四、注释

- **引用需求编号**：`# CR-16102600 / FR-03：……` —— 看代码能回查「为什么」。
- 写**为什么**，不写**是什么**。
- 用中文。
- **不留「临时」「先这样」和空 TODO**：要做就做，不做就进 `docs/待办.md` 并登记 CR。

## 五、可测性（写代码时就要想）

- 副作用集中且**可注入**（存储、时钟、外部 HTTP 客户端）。
- 时间相关逻辑接受参数注入，不在函数内部直接取当前时间。
- 错误路径**明确返回值**，不靠抛异常跨层传递；对外错误码按 `api/docs/01.项目API文档.md` 的约定。
- 访问宿主 / 第三方 API **包 try/except**（包括属性读取本身），并且**兜底逻辑不要依赖「加载期校验」**——配置错误往往在真正调用时才暴露。

## 六、测试

- **后端框架：pytest**（`api/pytest.ini`，用例在 `api/test/`，夹具 `api/test/conftest.py`，开发依赖 `api/requirements-dev.in`）。
- **前端框架：vitest**（`npm run test:unit`，用例在 `ui/src/**/__tests__/*.spec.ts`）。
- 用例名说清**验什么**，并标需求编号。
- 断言要**能证伪**：断言具体值，不断言「不为空」。
- 跑法写进测试文件头注释。
- **跑不跑由 `团队配置.md` 的测试策略决定**（`全量` / `仅回归` / `仅静态`；本项目另设 `后端端到端`，即只对后端真实 HTTP 链路打固定清单，见该文件「测试策略」节）。

## 七、提交

- 格式：`<type>(<scope>): <中文摘要>`，如 `feat(CR-16102600): 开放 API Playground`
- **一个提交一件事**：功能、文档同步、收尾补记录分开提。
- **不提交**可再生成物：`ui/dist/`、`docker/volumes/`、`api/storage/log/`、`开发文档/_汇总/`（已在 `.gitignore`）。
- **不提交任何 env / 密钥文件**：`docker/.env`、`api/.env`。
- 提交信息写清**已知缺口**（如「未跑自动化用例」）。

## 八、禁止事项

1. 不加外部依赖（要加走 CR）。
2. 不改已批准内容而不留痕。
3. 不覆盖审计（只追加；用户原话一字不改）。
4. 不把代码放进 `开发文档/`。
5. 不写死环境信息（IP、端口、路径）—— 走 env / 配置。
6. 不用 `innerHTML` 拼接用户输入。
7. 不为「看起来完整」造没人调用的代码。
8. **不在 Python 里硬编码模型名**（`gpt-4o-mini` 那类官方名在本项目的平台上不存在）。
9. **不把密钥、`.env` 内容、数据库口令写进仓库或 `开发文档/`**。

## 九、例外怎么处理

任何一条要破，先说清三件事：① 破哪一条；② 为什么这里不适用；③ 破完的代价是什么。
三条都写进当轮审计。**不写就默认没破过。**
