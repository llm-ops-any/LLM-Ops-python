- 选项：`A+B+C 全做` / `只做 A+C` / `只做 C` / `先不改`
- 选择：**A+B+C 全做**（接口脱敏 + 数据库加密 + 补 `account_id` 过滤）

  两个缺口必须一起堵，C 顺手且无感。

## D-02 编辑时密钥框的表现：掩码 + 不改则保留

- 时间：2026-10-29 21:33
- 决策人：张勇
- 选项：`掩码 + 不改则保留` / `掩码 + 强制重填` / `整个 value 不回传`
- 选择：**掩码 + 不改则保留**
- 理由：用户改插件名、改描述时不该被逼着重新粘贴一遍 `sk-`；同时保证页面与网络面板里不出现明文。

## D-03「不修改」用什么信号表达

- 结论：请求里 `value` 为空字符串（或仍等于掩码 `****`）都视为「沿用已保存的密钥」。
- 为什么不用更"严谨"的方案（比如传 diff、传 `keep: true` 标记）：`CreateApiToolReq.validate_headers`
  强制每个元素只能有 `key`/`value` 两个字段，加字段要改请求契约与前端表单；空值约定与仓库已有的
  `model_provider_service.save_config("api_key 为空表示不修改")` 完全同构，学习成本为零。
- 代价：无法通过接口把一个请求头的值**清空**成空字符串（要清空只能删掉该请求头）。可接受——
  空的 Authorization 头本身没有意义。

## D-04 加密粒度：整条请求头的 value 全加密，不挑"敏感头"

- 结论：只要 value 非空就加密，包括 `Content-Type: application/json`。
- 理由：按关键词挑敏感头（Authorization/api-key/token…）依赖命名习惯，漏判一个就是泄漏；
  统一加密只多花几次 Fernet 运算（单次微秒级），换来"存储里不存在任何明文"这条可验证的结论。

## D-05 复用 JSONB 里的 `encrypted` 标记，不新增字段

- 结论：`[{"key","value","encrypted"}]`，历史数据无 `encrypted` 按明文处理。
- 理由：零表结构变更，不必引入 alembic；同时天然支持"从旧备份恢复后重新跑迁移脚本"。

## D-06 解密失败不抛异常

- 结论：`decrypt_headers` 解密失败时把该请求头降级为空值并记 warning，请求照常发出。
- 理由：主密钥变更时，抛异常会让整个应用配置加载失败、连对话都发不出去；
  降级后用户只会看到"上游鉴权失败"，日志里有明确指向。**失败要可诊断，但不要扩散。**

## 回退方式

代码回退到本 CR 之前的提交；**数据必须同时回退**（旧代码读到密文会把密文当请求头发出去，全部鉴权失败）。

数据回退脚本（容器内执行，把密文解回明文并去掉 `encrypted` 标记）：

```python
from app.http.app import app
from internal.extension.database_extension import db
from internal.lib.secret import decrypt_secret
from internal.model import ApiToolProvider

with app.app_context():
    for provider in db.session.query(ApiToolProvider).all():
        plain = [
            {"key": h.get("key"), "value": decrypt_secret(h.get("value")) or ""}
            if h.get("encrypted") else h
            for h in (provider.headers or [])
        ]
        provider.headers = plain
    db.session.commit()
```

本次实际只涉及 1 个插件（博查AI）、2 条请求头，回退成本可忽略。
