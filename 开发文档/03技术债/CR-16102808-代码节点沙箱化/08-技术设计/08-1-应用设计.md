# CR-16102808 应用设计

## 一、总体结构

```text
API 进程（gunicorn worker）
  └ CodeNode._execute_function(code, params=...)
       ├ ① AST 静态检查（原有校验 + 新增危险节点拦截）
       ├ ② 组装请求 JSON → stdin
       ├ ③ subprocess.run(
       │      [sys.executable, "-I", "-S", runner.py],
       │      cwd=<新建临时空目录>,
       │      env=<最小白名单环境>,
       │      preexec_fn=<设资源上限>,
       │      timeout=5,
       │      start_new_session=True)
       └ ④ 解析 stdout JSON → 返回 dict
             │
             └── 子进程：sandbox_runner.py
                   ├ 读 stdin（code + params）
                   ├ 受控 exec(code)
                   ├ 调 main(params)
                   └ 结果写 stdout（JSON），异常写 err 字段
```

## 二、五层防御

| 层 | 手段 | 挡住什么 |
|---|---|---|
| **L1 进程隔离** | 独立 `subprocess` + `start_new_session=True` | 崩溃、死循环、`sys.exit()`、C 层 segfault 都不影响 API 进程 |
| **L2 资源上限** | `preexec_fn` 里 `resource.setrlimit` | CPU 时间、内存、可写文件大小、打开文件数 |
| **L3 环境净化** | `env` 只传 `PATH` / `LANG` / `PYTHONIOENCODING` | `os.environ` 拿不到 DB 串、JWT 密钥、平台 Key |
| **L4 静态拦截** | AST 扫描 `Import` / `Call` 节点 | 明显的 `import os/subprocess/socket/ctypes`、`eval/exec/open/__import__` |
| **L5 超时终止** | `subprocess.run(timeout=)` + 失败时 `os.killpg` | 超时后连带整个进程组杀掉，避免 fork 出子进程残留 |

> L1~L3 是「即使 L4 被绕过也还在」的兜底；L4 只是让常见越权更早给出**可读错误**，不是唯一依靠。

## 三、资源上限取值

| 限制 | 值 | 依据 |
|---|---|---|
| `RLIMIT_CPU` | 5 秒 | 代码节点是数据加工，正常毫秒级；5 秒足够，且与 subprocess timeout 对齐 |
| `RLIMIT_AS` | 512 MB | 允许处理几万条记录；再大就该分页而不是塞内存 |
| `RLIMIT_FSIZE` | 0 | **完全禁写文件**（现有节点不写盘，需要落文件应走上传/存储接口） |
| `RLIMIT_NOFILE` | 64 | 防止开一堆 fd |
| `timeout` | 5 秒 | 与 `RLIMIT_CPU` 双保险：CPU 限制管「算太久」，timeout 管「卡在 IO 上不动」 |

> `RLIMIT_NPROC` **不设**：容器内 uid 是 root，root 不受 NPROC 限制，设了是假防护；fork 炸弹的兜底靠 `killpg`。

## 四、环境变量白名单

```python
SAFE_ENV = {
    "PATH": "/usr/local/bin:/usr/local/sbin:/usr/sbin:/usr/bin:/sbin:/bin",
    "LANG": "C.UTF-8",
    "PYTHONIOENCODING": "utf-8",
    "PYTHONDONTWRITEBYTECODE": "1",
}
```

**不传**：`SQLALCHEMY_DATABASE_URI`、`JWT_SECRET_KEY`、`REDIS_*`、`OPENAI_*`、`GAODE_*`、`DASHSCOPE_*` 等全部。

## 五、AST 拦截规则

### 5.1 禁止的 import（模块名命中即拒，含子模块）

```
os, sys, subprocess, socket, ctypes, shutil, importlib, builtins,
multiprocessing, threading, signal, resource, pty, fcntl,
pathlib, glob, tempfile, fileinput, io 的 open 使用
```

> `sys` 也禁：`sys.modules` 可以拿到已加载的危险模块。

### 5.2 禁止调用的名字（`ast.Call` 的 func 是 Name 时）

```
eval, exec, compile, open, __import__, breakpoint, input,
globals, locals, vars, getattr, setattr, delattr
```

> `getattr` 也禁：`getattr(__builtins__, 'eval')` 是常见绕过。

### 5.3 允许的模块（白名单，其余一律拒）

```
json, math, re, datetime, time, random, uuid, hashlib, base64,
itertools, functools, collections, string, decimal, statistics,
urllib.parse, html, textwrap, csv, io 之外的标准库不保证
```

> 采用**白名单**而不是黑名单：黑名单永远补不全，白名单漏了再加。
> 现有工作流只用 `json/hashlib/base64`，已覆盖。

## 六、错误提示（要人能看懂）

| 场景 | 提示 |
|---|---|
| import 不在白名单 | `代码中不允许导入模块 xxx（白名单：json、math、re…）` |
| 调用禁用函数 | `代码中不允许调用 xxx` |
| 超时 | `代码执行超时（超过 5 秒），请检查是否有死循环` |
| 内存超限 | `代码执行内存超限（上限 512MB）` |
| 其他异常 | 保留原有 `Python代码执行出错`，并把子进程的 err 附在日志里 |

> 对外仍走 `FailException`，**不改变接口契约**。

## 七、兼容性

| 现有用法 | 是否受影响 |
|---|---|
| `import json / hashlib / base64` | ✅ 白名单内 |
| 纯计算（循环、字典、字符串） | ✅ |
| `main(params)` 返回 dict | ✅ 契约不变 |
| 原有 5 类校验错误 | ✅ 提示文案一字不改 |
| 代码里 `import os` 之类（若有其他工作流） | ⚠️ **会被拒** —— 这是本次的**目的**，但需在验收时确认没有误伤 |

## 八、性能

每次调用起一个 Python 进程。实测冷启动约 30~50ms（`-S` 跳过 site 导入可再省）。

对比：工作流一次 LLM 调用通常 1~10 秒，节点开销可忽略。
