# CR-16111410 决策记录

## D-01 清单来源：`docker compose config --images`（选中）

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| A. 脚本从 compose 现场取 | 与编排永不漂移；换版本只需重跑 | 必须在 `docker/` 体系内运行 | **选中** |
| B. 写死 6 个镜像名 | 脚本可在任何目录跑 | compose 改版本后静默漏包，直到新机器 `up -d` 才炸 | 否 |
| C. 从 `docker images` 里筛 `llmops-*` | 不用 compose | 拿不到第三方镜像的来源关系，且会把无关项目镜像混进来 | 否 |

## D-02 不压缩（选中）

- 实测：`docker images` 虚拟大小合计 ~3.3 GB，导出后 **489 + 266 MB** —— Docker 29（containerd 存储）导出的 OCI 层本身是压缩 blob。
- 再加 gzip：Windows 无稳定内置 gzip；`Compress-Archive` 对 GB 级 tar 慢、失败要重来；收益小。
- 结论：交给传输介质（U 盘 / 网盘自带压缩与断点续传）。

## D-03 切成 2 个包（选中）

- 改动频率不同：应用镜像随代码变，第三方（redis/postgres/weaviate/nginx）很少变。
- 单包体积可控 ⇒ 断点重传代价小；新建目录 `offline-images/` 也便于整体拷贝。

## D-04 保留 OCI 布局原样（非决策，记录事实）

- Docker 29 的 `docker save` 输出 `blobs/` + `index.json` + `oci-layout`，**没有**旧的 `manifest.json`。
- 已实测 `docker load` 可正确还原 `repo:tag`（T-05），不转格式、不手工改包。
- 因此本 CR 的 AC-03 实际按「`index.json` 可解析」验收，验收报告已注明差异。

## D-05 脚本用中文名 + 写 UTF-8 BOM

- 中文名：与仓库「产物命名中文」一致，用户口语可直接命中。
- BOM：Windows PowerShell 5.1 读无 BOM 的 UTF-8 中文脚本会乱码甚至语法错；写入 BOM 一次，两端都能跑。

## D-06 不改 compose、不加 `image` 到本地仓库

- 有人会想到「把镜像 push 到内网 registry 给另一台机拉」，但那需要额外起 registry / 配 insecure-registry，
  属于新的基础设施（新 CR 才做）；本 CR 只解决「拷文件过去」这一条最短路径。
