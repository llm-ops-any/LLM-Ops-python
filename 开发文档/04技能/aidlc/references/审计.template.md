# 审计

> **整份复制**到 `开发文档/<类型目录>/CR-<8位号>-<简称>/40-审计-<人>.md` 再填。
> **一人一份**（`40-审计-张勇.md` / `40-审计-李四.md`），**不写公共 `审计.md`**。
>
> 三条铁律：
> 1. **只追加，永不覆盖**（规则 C）。改错了不删旧条，追加一条「更正上一条」。
> 2. **不改写、不概括用户的原始输入**。用户说「视角反了」就写「视角反了」，不要润色成「视角朝向存在偏差」——
>    以后复盘时，原话才是能对得上用户记忆的东西。
> 3. **每条记录的时间是真实的写入时刻**，不是这条 CR 的创建时刻。多条记录挤在同一秒 = 事后批量补写，
>    审计就失去了「什么时候决定了什么」的作用。

---

## 什么事件要记

| 场景 | 记 |
|---|---|
| 缺陷登记 / 需求受理 | ✅ 用户原话 + 初判方向 |
| 每轮修复交付 | ✅ 改了什么 + 怎么验的 + 交付了哪些文档 |
| 用户推翻上一轮结论 | ✅ 用户原话 + 因此作废了什么 |
| 用户批准门禁 / 接管项目 | ✅ 批准动作本身 |
| 阶段跳跃（跳过某阶段） | ✅ 跳过的理由 |
| 微改动的即时处理 | ✅ 时间 / 改了什么 / 为什么算微改动（三项缺一不可） |
| 改了某行代码、跑了个命令 | ❌ 这是过程不是决策，留在 `20-测试记录.md` |
| 我在对话里的思考过程 | ❌ 只记结论 |

## 单条格式

```markdown
## 2026-10-30T10:22:29+08:00｜缺陷登记与实施

- User：张勇
- Email：zhangyong@uino.com
- 用户原始输入：资产管理--透视-逻辑空间的视角反了，应该旋转180就对了，可以参考同屏模式下的视角（附两张截图）
- Decision：定位为保存视角分支的 up 与俯视视线平行导致 lookAt 退化，把该分支 up 固定为 GraphLayout.camera.upDirection；不改布局与保存视角数据。
- Basis：该视角只存 position/target，滚转只能由 up 决定，而旧代码取进入前的世界 Y 轴。团队配置规定 02缺陷不设 G1，测试策略 `仅静态`。
- Auto：是；不加依赖、不改接口、不自动提交。
```

### 字段说明（六个字段，一个都不能少）

| 字段 | 写什么 | 常见错法 |
|---|---|---|
| 标题 | `ISO 时间｜一句话阶段名` | 只写日期不写时刻；时刻精确到秒但同一秒重复多条 |
| `User` / `Email` | 决策人，两者都要 | 只写名字，事后分不清是谁的子账号 |
| `用户原始输入` | **逐字抄**，可含错别字、口语、粘贴的代码块 | 概括成一句话；把用户的第二句话合并进第一条 |
| `Decision` | 决定了什么（**做了什么**，不是"要做什么"） | 写成计划；写成"开始分析" |
| `Basis` | **凭什么**：读到的代码 / 规则文件 / 用户授权。引用规则要写文件名 | 写"根据经验"；写"用户要求"但不说是哪句 |
| `Auto` | 这次是不是自动决定的；自动决定必须能在 `30-验收报告.md` 的「自动决定」里找到对应 | 写"是"却不说自动决定了哪些参数 |

## 多条记录的排序与编号

- 严格按时间**正序**追加在文件末尾。
- 同一天多轮跟进，不要合并成一条 —— 用户推翻一次结论就是一个独立事件。
- **交付类记录**（"XX 交付"）和**开始类记录**（"XX 开始"）是两个时刻，不要用同一个时间戳。

## 交付前对照

- [ ] 用户原始输入是逐字原文，没有润色
- [ ] 每个时间戳都不重复（除极少数真同秒事件，且能解释）
- [ ] 每条 `Auto：是` 的决定，都在 `30-验收报告.md` 的「自动决定」表里有对应行
- [ ] 没有覆盖或删除过任何历史条目
