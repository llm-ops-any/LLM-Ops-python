# CR-16111410 设计：离线镜像包怎么产、怎么用

## 一、清单从哪来（唯一来源）

```
docker/ ─ docker compose config --images | Sort-Object -Unique
        ⇒ llmops-api:0.1.0
          llmops-ui:0.1.0
          nginx:latest
          postgres:15-alpine
          redis:6-alpine
          semitechnologies/weaviate:1.28.4
```

**不手写第二份清单**：compose 里改版本号后，脚本自动跟上；手写列表必然腐化，且腐化时不报错，
到另一台机 `up -d` 才会发现「镜像不存在、又去联网拉」。

## 二、包怎么切（2 个 tar）

| 包 | 内容 | 实测体积 | 为什么这么切 |
|---|---|---|---|
| `llmops-app-0.1.0.tar` | `llmops-api:0.1.0`、`llmops-ui:0.1.0` | ~2.4 GB | 本地构建产物，**换机必带**；版本号随 tag 走 |
| `llmops-thirdparty-20261114.tar` | redis / postgres / weaviate / nginx | ~1.0 GB | 上游公共镜像，**很少变**，可以长期复用；单独打包不必每次重导 |

切两刀的理由：重导一次只改应用镜像，第三方包可反复用；单包 ≤2.4 GB，断点重传代价可控。

## 三、怎么产出

`docker/offline-images/导出镜像.ps1`（在 `docker/` 下执行）：

1. `docker compose config --images` 取清单、去重、排序；
2. 逐个 `docker image inspect` 确认**本地存在**，缺一个就停（不允许静默漏包）；
3. `docker save -o out.tar <img...>` 按上表分组导出；
4. `Get-FileHash -Algorithm SHA256` 生成 `SHA256SUMS.txt`；
5. 打印「镜像 → tar」映射与体积，供人工核对。

幂等：重跑覆盖同名 tar；已存在同 tag 的旧包不会自动删（避免误删历史版本），由人决定。

## 四、怎么用（另一台机）

`docker/offline-images/导入镜像.ps1`：

1. 校验 `SHA256SUMS.txt`（`Get-FileHash` 逐条比对，不一致立刻停）；
2. `docker load -i` 两个 tar（同名 tag 会被覆盖成包内版本，属预期）；
3. 输出 `docker images` 中这 6 个镜像的行，供人确认。

起服务仍是既有流程（`部署规范.md` 第三节）：准备 `docker/.env` → `docker compose up -d`（**不带 `--build`**）
→ `docker compose restart llmops-nginx` → 最小验收 4 条。

## 五、与既有 CR / 规则的关系

- `CR-16102702-容器化部署`：编排与镜像清单的来源，本 CR 只消费不改。
- `CR-16111409-本机数据导出快照`：数据走 `docker/postgres/llmops_data.sql`，镜像包**不含**数据，二者一起才叫「换机还原」。
- `部署规范.md`：新增「离线镜像」小节；「改了什么 → 执行什么」表和硬禁区不动。

## 六、明确不做

- 不打 gzip：Windows 无稳定内置 gzip，`Compress-Archive` 对 GB 级 tar 慢且中途失败要重来；
  传输时由网盘/U 盘负责压缩与断点（见 `决策记录.md` D-02）。
- 不导出构建基础镜像：本机 Docker 内没有 `python:3.10-slim-bookworm` / `node:20`（api/ui 镜像是构建后残留的运行镜像），
  `docker save` 只能存本地已有的镜像 ⇒ 重建能力不在本包范围内（遗留 L-01）。
