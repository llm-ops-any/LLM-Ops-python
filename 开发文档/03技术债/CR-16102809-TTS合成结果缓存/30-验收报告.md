# CR-16102809 验收报告

> 结论建议：**通过**。7/7 AC 全绿，接口与前端零改动，回归无异常。

## 一、修好了什么

**改之前**：同一条消息每点一次「朗读」就重新合成一次、**计费一次**。用户反复听 3 次就是 3 倍成本。

**改之后**：同一条消息 + 同一引擎 + 同一音色 → **只合成一次**，之后直接回放缓存。

## 二、实测

| AC | 结果 |
|---|---|
| 第二次请求不再调 provider | ✅ calls 停在 1 |
| 两次音频一致 + 都有 tts_end | ✅ 3 块 vs 3 块 |
| 换音色重新合成 | ✅ calls=2，内容不同 |
| 中途断开不写缓存 | ✅ 无文件产生 |
| 过期缓存清理 + 重合成 | ✅ |
| 损坏缓存丢弃 + 重建 | ✅ |
| 冒烟（语音接口 / SSE） | ✅ |

全程用**假 provider**，不消耗阿里百炼额度。

## 三、我替你决定的（请过目）

| # | 决定 | 理由 |
|---|---|---|
| 1 | 缓存**存文件**（`storage/tts_cache/`），不塞 Redis/DB | 音频 1 分钟约 2.6MB，Redis 内存和 DB 表都扛不住；`storage/` 已挂载可写 |
| 2 | key 里带 **engine + 音色/模型指纹 + 文本指纹** | 换音色必须重合成，否则播错人声；答案变了自动失效 |
| 3 | **只缓存完整结果**，中途断开不写 | 半截音频会让播放突然断掉 |
| 4 | TTL **7 天**，单文件上限 **20MB**，**惰性清理** | 不引定时任务，访问时顺手删过期的 |
| 5 | 命中时仍按 **SSE 逐块**发送 | 前端一行代码都不用改 |
| 6 | 并发同一消息**不做锁** | 最坏浪费一次调用，加分布式锁的复杂度不值 |

## 四、已知边界

1. **首次合成仍计费**，缓存只解决"重复听"。典型收益约省 2/3。
2. **多机部署时缓存不共享**（本地文件）。当前单机，不构成问题；上多机要换 COS。
3. **磁盘会涨**。有 TTL + 上限兜底，构建说明里给了手工清理命令。
4. **长时间运行效果未观测**，需要跑几天看目录大小。

## 五、安全提示

缓存目录**绝不能**挂到 nginx 静态路径。那会绕过 `created_by` 校验，任何人可下载他人语音。
当前实现只在 `audio_service` 内部读写，文件路径不对外暴露。
