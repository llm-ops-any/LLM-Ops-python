# CR-16102807 决策记录

## D-01 按原项目「公众号」通道实现，不走微信客服中间件

- **背景**：`待办` N1 提过两条路 —— ① 补公众号（本方案）② 走微信客服/企微中间件。
- **决策**：本 CR 做**公众号**通道。
- **理由**：PO 明确「做公众号那个任务」；且公众号方案在项目内有完整参考实现（原项目 7 文件），移植成本可控；企微中间件是外部系统，不在本项目代码范围内。
- **被否**：企微中间件 —— 需要另一套凭证体系与外网服务，与本项目「应用发布」的模型不匹配。

## D-02 保留「异步子线程 + 回复 1 拉取」的交互，不改同步返回

| 方案 | 问题 |
|---|---|
| A. 同步跑完再回复（选） | 微信要求 **5 秒内**响应，Agent 常跑 10~100 秒，必然失败 |
| B. 异步 + 「回复 1」拉取（**选中**，原项目做法） | 用户多一步操作，但不会超时 |

- **决策**：沿用 B。
- **理由**：这是微信被动回复模式的**硬约束**（5 秒超时后会重试 3 次，导致重复执行），不是设计偏好。
- **被否**：A —— 技术上不可行。
- **代价**：用户体验上要多发一个「1」。原项目同样如此。

## D-03 用 `wechatpy` 而不是手写 XML/签名

| 方案 | 成本 |
|---|---|
| A. 手写（hashlib + xml.etree） | 零依赖，但签名排序、XML CDATA、回复渲染都要自己实现，易出错 |
| B. `wechatpy`（选中） | +1 个依赖（原项目同款 1.8.18），`check_signature` / `parse_message` / `TextReply` 现成 |

- **决策**：选 B。
- **理由**：原项目已验证；协议细节（尤其 XML CDATA 与签名算法）手写风险高于收益。
- **被否**：A —— 省一个依赖但增加协议 bug 面。

## D-04 密钥（AppSecret）明文回显，不加密

- **事实**：原项目 `GetWechatConfigResp` 直接返回 `wechat_app_secret` 明文。
- **决策**：**沿用原项目行为**，本次不改。
- **理由**：这是 PO 自己的公众号凭证，且页面只有登录态可访问；改成加密+掩码会偏离原项目、增加改动面。
- **被否**：像 `CR-16102803` 语音 Key 那样加密存储 + 掩码回显。
  **如果 PO 要求统一口径，可另开 CR 处理**（需要加解密工具与前端「留空表示不修改」逻辑）。
- **记录理由**：这是**已知的安全口径不一致**，必须显式告知，不能默认。

## D-05 `SERVICE_IP` / `SERVICE_API_PREFIX` 走环境变量，不写库

- **决策**：与其他设施配置一致，放 `docker/.env` + compose 公共锚点，后端读环境变量下发。
- **理由**：换公网地址时改一处、重启即可，不用动数据库。
- **被否**：存 `platform_setting` 表 —— 会让「部署参数」和「业务配置」混在一张表，且改地址要开页面。

## D-06 迁移新建 revision，不复制原项目迁移文件

- **决策**：新建 revision，`down_revision = b7d21e9c4a55`（本项目当前 head），表结构照原项目、但**不引入原项目的 `493395dc50b8`（加 `image_urls`）**。

- **✅ 已核对**：`wechat_service` 里写 `Message(... image_urls=[])` 的那行**必须改成 `attachments=[]`**，否则插入报错。

## D-07 表名与既有 `platform_setting` 不冲突

- **事实**：`CR-16102803` 已建 `platform_setting` 表（键值型配置）。
- **决策**：新表用原名 `wechat_config` / `wechat_end_user` / `wechat_message`。

## D-08 修掉原项目的 openid 取值 bug（`msg.target` → `msg.source`）

- **发现**：移植后实测 `parse_message` 的语义 —— `source = FromUserName`（用户 openid）、`target = ToUserName`（公众号 id）。
  原项目写 `openid = msg.target`，取到的是**公众号自己的 id**。
- **后果（若不修）**：所有微信用户会落到同一条 `wechat_end_user` 记录上，表现为**会话与历史全部串号**，且只有一个"用户"。
- **决策**：改为 `msg.source`。
- **理由**：原项目注释「发送方账号，数据其实是openid(FromUserName/source)」已经写明本意是 source，只是代码写错。这是上游缺陷，不应照抄。
- **验证**：实测 `o_user_A` / `o_user_B` 两个 openid 分别建了独立 `wechat_end_user` 与独立 `end_user`。
- **决策人**：DEV（依据实测）。

## D-09 tiktoken 编码文件预置进镜像（原项目无此问题，因本项目多了一处 token 统计）

- **现象**：子线程卡在 `agent.invoke` 不返回，也不报错，用户永远看到「处理中」。
- **定位**：`faulthandler` dump 线程栈，卡点明确 ——
  `model_entity.get_num_tokens_from_messages` → `tiktoken.get_encoding("cl100k_base")` → `requests.get` 下载 BPE 文件（`ssl.read`）。
  国内访问 `openaipublic.blob.core.windows.net` 极慢，实测数分钟。
- **为什么原项目没暴露**：原项目未处理这种「请求已返回、子线程还在跑」的场景；一旦碰上同样会卡，只是没人等那么久。
- **决策**：把 `cl100k_base` 编码文件（1.7MB）预置到 `api/docker/tiktoken_cache/`，镜像里设 `TIKTOKEN_CACHE_DIR` 指向它。
- **理由**：默认缓存在 `/tmp/data-gym-cache`，容器重启即清空，每次都要重下；预置后**运行时零联网**，实测耗时从「分钟级」降到 **0.195 秒**。
- **被否**：构建时 `RUN python -c "tiktoken.get_encoding(...)"` 预热 —— 构建环境同样受网络影响，可能把构建拖到超时，且失败时不易察觉。
- **影响面**：不只微信，**普通聊天/SSE 的 token 统计同样受益**（它们也在流结束后调同一函数）。

## D-10 子线程异常必须落状态，不能只打日志

- **现状**：原项目 `_thread_chat` 无 try/except，线程内异常只打到进程 stderr，用户在微信里永远看到「处理中」。
- **决策**：`_thread_chat` 外层统一兜住 → 写 `logging.exception` + 把 `message.status` 改为 `error` 并写入 `error` 字段。
- **效果**：用户回复「1」时能看到「该Agent智能体处理任务出错…错误信息: xxx」，而不是无限等待。
- **决策人**：DEV。
