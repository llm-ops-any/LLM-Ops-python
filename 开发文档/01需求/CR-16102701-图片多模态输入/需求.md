## 1. 用户原话（一字不改）

> A 平台补多模态（正解）(在 LLM-Ops-python 另开 CR，把 kind=image 附件构造成多模态 content，用 IMAGE_INPUT 做开关；视觉模型已有 qwen3-vl-plus / deepseek-v4-flash-vision-exp。改完要 docker compose build llmops-api + restart llmops-nginx)

来源背景（`CR-16102601` 状态.md 遗留项）：

> CR-16102601 遗留（无人卡住，登记备查）：AC-03 上传失败提示与 R-02 COS 故障分支未构造；真多模态（图片看懂）另开 CR。

触发方：`ui-to-code` 项目 `CR-16102700` 诊断结论——平台收到 `kind=image`、`text=""`、只有 `url` 的附件后，
`build_query_with_attachments` 只把「文件地址：<url>」拼成文本，模型从未收到图片像素，导致生成结果与截图无关。

## 2. 目标

1. **图片真的进模型**：当模型支持图片输入时，`kind=image` 且只有 `url` 的附件以多模态内容（`image_url`）随消息送入。
2. **不做能力假设**：模型不支持 `image_input` 时行为与改造前**完全一致**（URL 文本注入），不允许出现「传了图却拿到空回答」。
3. **四条链路同步生效**：开放 API `/openapi/chat`、应用调试对话、WebApp、辅助 Agent 共用同一份实现。
4. **对外契约说清楚**：`api/docs/01.项目API文档.md` 写明白「`kind=image` 的 `url` 在视觉模型下会被当作图片传入」。

## 3. 范围

### 3.1 做

- 新增构造器：把「提问 + 附件」构造成 `str` 或多模态 `list`（模型支持图片输入且存在图片附件时返回 `list`）。
- 4 处 `HumanMessage(build_query_with_attachments(...))` 改为按模型能力二选一。
- Agent 兼容 `content` 为 `list`：输入审核取文本部分、历史消息重建不丢 `content`、token 统计计入文本部分。
- 回写 `api/docs/01.项目API文档.md`。

### 3.2 不做（明确排除）

| 不做 | 理由 |
|---|---|
| 改前端（Playground / 主页 / WebApp 附件 UI） | 附件上传与 `files` 直传已由 `CR-16102601` 打通，本次只补后端消费 |
| 图片压缩、缩放、base64 内联 | 中转平台实测能直接拉 COS 公网 URL 看图（见 `前置资源.md`），内联会让请求体膨胀数 MB |
| OCR / 图片文本解析 | 视觉模型直接理解版式与配色，OCR 只能救文字；且不引入新依赖 |
| 历史轮次重放图片 | 落库仍是元信息（`Message.attachments` 不含图片正文），刷新后模型看不到上轮图片——已知边界，写入文档 |
| 改附件数量 / 体积上限 | 沿用 `MAX_CHAT_ATTACHMENT_COUNT` 等既有常量 |
| 迁移数据库 | 无表结构变更 |
| 替用户改应用配置里的模型 | 应用归属 PO；只出指引（见 §5 AC-01 前置步骤） |

## 4. 功能需求

### FR-01 多模态内容构造

新增 `build_human_message_content(query, attachments, supports_image)`：

- `supports_image=True` 且附件中存在 `kind=image`、`text` 为空、`url` 为 `http(s)` → 返回 `list`：
  `[{"type":"text","text": <提问 + 文本类附件上下文 + 图片说明>}, {"type":"image_url","image_url":{"url": ...}}, ...]`
- 其余情况返回与改造前**逐字一致**的 `str`（保证非视觉模型零回归）。
- 图片按附件顺序排列，数量受 `MAX_CHAT_ATTACHMENT_COUNT` 约束；无 `text` 的非图片附件仍按 URL 文本注入。

- **AC-01** 视觉模型 + 1 张截图（`text=""`）问「蓝色按钮上的四个字」→ 答「百度一下」。
- **AC-02** 同一请求换非视觉模型（`deepseek-flash`）→ 输出与改造前同量级，不出现空回答、不报错。
- **AC-03** 同时带 `txt`（有 `text`）与图片 → 文本内容仍进上下文，模型能同时引用文字与图像。

### FR-02 能力开关

- 用 `ModelFeature.IMAGE_INPUT in llm.features` 判定，不写死模型名（`00规则/开发规范.md` §八.8）。
- 开关为假时禁止构造 `list`。

- **AC-04** 代码级复核：4 条链路均以 `llm.features` 判定，无模型名硬编码（`grep -n "qwen3-vl\|vision-exp"` 在 `api/internal` 下应为 0 命中）。

### FR-03 四条链路一致

`openapi_service`、`app_service`、`web_app_service`、`assistant_agent_service` 全部改造。

- **AC-05** 开放 API curl 可复现 AC-01（后端端到端，真实 HTTP）。

### FR-04 Agent 兼容 `content` 为 list

- 输入审核：从 list 中提取 `type == "text"` 的内容做敏感词判断。
- 历史消息重建：`HumanMessage(content)` 原样保留 list，不转字符串。
- token 统计：list 时累加各 `text` 片段；图片不计（无法用 tiktoken 编码），文档写明统计偏低。

- **AC-06** 开启输入审核并命中敏感词时，带图消息同样被拦下（不因 content 是 list 而漏判）。

### FR-05 对外文档

- `api/docs/01.项目API文档.md` 的 `/openapi/chat` `files` 段补充：`kind=image` 的 `url` 在视觉模型下作为图片传入；非视觉模型退化为 URL 文本。

- **AC-07** 文档含该说明且与实现一致。
