## 三、P0：语音闭环（ASR ＋ TTS）

### 3.1 第 0 步：探测结果（**2026-10-28 10:52 实测完毕**）

对中转平台 `token.uino.com/v1`（当前 API Key 所属分组：标准档 / distributor）逐项打点，结论如下。

**① 模型清单里没有任何 TTS 模型，只有一个疑似 ASR 的 `fun-asr`**

`GET /models` 返回 32 个模型，全部为对话 / 视觉 / 向量 / 生图类，与语音相关的只有一项 `fun-asr`（阿里 FunASR）。

**② TTS（文本转语音）：彻底不可用**

`POST /audio/speech` 逐个试 8 个候选模型名，**全部 503 `model_not_found`**：

| 试过的模型名 | 结果 |
|---|---|
| `tts-1` / `tts-1-hd` / `gpt-4o-mini-tts` | 503 `model_not_found`（`No available channel for model ... under group 标准档`） |
| `cosyvoice-v1` / `cosyvoice-v2` / `qwen-tts` / `qwen-audio-tts` / `sambert` / `sovits` | 503 `model_not_found` |

**③ ASR（语音转文本）：名义上有 `fun-asr`，两条路都走不通**

| 走法 | 结果 |
|---|---|
| `POST /audio/transcriptions`（`fun-asr`，wav / mp3） | **500 `convert_request_failed` / `not implemented`** —— 网关未适配该协议 |
| 同上传 webm | 500 `count_token_failed`（能读到文件、卡在解析） |
| `POST /chat/completions` + `input_audio`（OpenAI 原生 / DashScope data-URI / text+audio 三种格式） | **404 `Unsupported model fun-asr for OpenAI compatibility mode`** |
| `whisper-1` / `whisper-large-v3` / `paraformer-v2` / `sensevoice` | 503 `model_not_found` |

> 📌 与平台既有的「**没有可用生图能力**」是同一类结论：**语音/音频能力在该账号档位下同样为零**。`fun-asr` 出现在清单里但无可用渠道，属"挂名"。

**④ 一个意外的好消息：阿里语音的 SDK 早已在镜像里**

```
dashscope 已安装（requirements 里 dashscope==1.22.1 仍在）
dashscope.audio.tts_v2.SpeechSynthesizer  → 可正常 import
dashscope.audio.asr.Recognition           → 可正常 import
websocket-client==1.8.0                    → 已在（DashScope 流式 TTS 依赖它）
docker-compose.yaml 已透传 DASHSCOPE_API_KEY
```

⚠️ 但 `.env` 里 `DASHSCOPE_API_KEY=` **是空值**（键在、值为空）⇒ **要接阿里语音，需要张勇去阿里云百炼申请一个 Key**，代码侧零改动即可复用。

### 3.2 结论：方案改为「B′ 双轨」

| 能力 | 走什么 | 前置 |
|---|---|---|
| **ASR** | ① **默认**：保留 `ChatInputBar` 现有**浏览器 Web Speech API**（已实现，零成本）② **增强**：DashScope `paraformer-realtime` 走 `/audio/audio-to-text`（需 Key） | 增强档需 `DASHSCOPE_API_KEY` |
| **TTS** | **只能用 DashScope `cosyvoice-v2`**（原项目那套 OpenAI `tts-1` 在本平台**永远不可能工作**） | 需 `DASHSCOPE_API_KEY` |

**因此 §3.3 后端清单的实质变化**：`audio_service` **不再移植原实现**，而是写一个薄适配层，把「统一接口」与「具体厂商」解耦，将来平台若开通语音，加一个 provider 即可：

```
AudioService.audio_to_text(file)        →  provider.asr(file)
AudioService.message_to_audio(msg, acc) →  provider.tts_stream(text)  yields base64 chunk
```

- `DashScopeProvider`：`Recognition`（ASR）／`SpeechSynthesizer`（TTS，`stream=True` 返回 base64 片段）
- `OpenAICompatProvider`：保留原实现（`/audio/transcriptions`、`/audio/speech`），**默认不启用**，等平台开通后一个开关切过去
- 选择依据：`DASHSCOPE_API_KEY` 有值 → DashScope；否则 → 探测 OpenAI 兼容端点；都不行 → 接口返回明确的「未配置语音服务」业务错误（**不要 500**）

> 🔊 **前端契约完全不变**：`/audio/message-to-audio` 仍返回 SSE `tts_message` / `tts_end` 事件，`useAudioPlayer` 的 `MediaSource` 流式播放照原样用 —— 只是音频数据由 DashScope 产出。

### 3.5 验收

1. 编排页出现「语音转文本」「文本转语音」两项，开关可保存、刷新后保持（落 `app_config_version` 草稿）。
2. **未配 `DASHSCOPE_API_KEY` 时**：调用语音接口返回**明确业务提示**（如「未配置语音服务」），**不是 500**；前端录音按钮不可用或回退浏览器识别。
3. 配好 Key 后：开启语音转文本 → 三个聊天入口都能录音并回填文字。
4. 开启文本转语音 → 消息出现播放按钮，点击**边收边播**。
5. 关闭开关 → 按钮消失；`SERVICE_API`（开放 API）消息调 TTS 返回明确业务错误。
6. `npm run type-check` ＋ `npm run lint` 通过。

### 3.6 风险

- **`DASHSCOPE_API_KEY` 是硬前置**：没有它，TTS 这条链**一行代码都验不了**。申请 Key 属于业务动作，需张勇定。
- **DashScope 计费**：CosyVoice 按字符计费；原实现每次点击都重放整段，**不做缓存就会重复烧钱**。建议在 `audio_service` 里按 `message_id + voice` 做一层短 TTL 缓存（原项目没有，属改进项）。
- **`js-audio-recorder` 需要麦克风权限**：非 HTTPS / 非 localhost 页面浏览器直接拒绝 ⇒ 当前 nginx 是 IP ＋ HTTP 直服，**局域网 IP 访问时录音会失败**。要么恢复 HTTPS，要么只用现有 Web Speech API。
- **流式播放兼容性**：`MediaSource` ＋ `audio/mpeg` 在 Safari 需 `audio/mp4`；原实现未处理，本次保留原实现并加注释。

### 4.6 验收

1. 应用发布页出现公众号渠道；填齐三项且应用已发布 → 状态变「已配置」；应用退回草稿 → 状态自动回「未配置」。
2. 公众号后台填回调 URL 后点「提交」能通过校验（GET `echostr` 回显成功）。
3. 公众号发一条文本 → 5s 内回「思考中，请回复"1"」；再发 `1` → 返回答案。
4. 未发布应用 / 未配置应用 → 回明确的业务提示（不是 500）。
5. 重启后 celery 无异常（微信分支不依赖 celery，但共用一个镜像）。

### 4.7 风险

- **是否要这个功能值得先想清**：`docs/待办.md` N1 已登记「**Flash 中间件桥接微信客服**」路线（新建独立 Flask 小项目调开放 API，**不改 LLMOps**）。**公众号（订阅号/服务号）走 nginx 直连** 和 **微信客服走中间件** 是两条不同通道 —— 若未来主攻「微信客服」，本次补的公众号代码价值有限。
- 原实现**只支持文本消息**、**无 AES 加密模式**、**无消息去重**（微信会重试推送，原代码没做 `MsgId` 去重 ⇒ 可能重复建消息、重复计费）。
- 子线程直接跑 Agent：**gunicorn 多 worker 下线程随进程回收**，长任务有丢失风险（原项目如此，本方案不改）。
