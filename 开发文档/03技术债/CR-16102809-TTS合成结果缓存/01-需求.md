# CR-16102809 需求：TTS 合成结果缓存

- **需求性质**：增量（技术债）
- **类型**：技术债（只改内部实现，接口与前端无感）
- **来源**：`CR-16102803` 遗留项「TTS 无缓存会重复计费」

## 一、问题

`message_to_audio` 每次调用都**重新走一遍 provider 合成**。

- 用户对同一条消息点两次「朗读」→ 合成两次 → **计费两次**
- 换设备 / 刷新页面再听 → 又算一次
- 一条 500 字的答案，CosyVoice 合成成本按字符计费，重复听 3 次就是 3 倍成本

## 二、目标

| # | 目标 |
|---|---|
| G-01 | 同一条消息 + 同一引擎 + 同一音色 → **只合成一次**，后续直接回放 |
| G-02 | 前端**完全无感**：仍是同一套 SSE 事件（`tts_message` / `tts_end`），块大小可不同 |
| G-03 | 引擎或音色切换后**必须重新合成**（缓存不能跨配置复用） |
| G-04 | 中断的合成**不写入**缓存（避免缓存半截音频） |
| G-05 | 磁盘可控：单文件上限 + TTL 过期清理 |

## 三、不做

| # | 不做什么 | 原因 |
|---|---|---|
| 1 | 缓存到 Redis / 数据库 | 音频体积大（1 分钟约 2.6MB PCM），Redis 与 DB 都不适合；`storage/` 已挂载可写 |
| 2 | 上传到 COS 再做 CDN | 增加外部依赖与鉴权，当前单机场景收益不足 |
| 3 | 预生成（消息一产生就合成） | 大部分用户不点朗读，预生成纯浪费 |
| 4 | 并发去重（同一消息同时只合成一次） | 需要分布式锁；重复合成的代价只是浪费一次调用，先不做 |
| 5 | 文本分段合成的中间缓存 | 只缓存完整结果，逻辑简单且不会有"拼接错乱"风险 |

## 四、验收标准

| AC | 内容 | 判定 |
|---|---|---|
| AC-01 | 同一消息连续请求 2 次，**第 2 次不再调用 provider** | provider 加计数器 / 看日志 |
| AC-02 | 第 2 次返回的音频内容与第 1 次**一致** | 比对 base64 累加值 |
| AC-03 | 切换引擎或音色后**重新合成**（缓存未命中） | 改配置再请求 |
| AC-04 | 前端无改动仍能正常播放 | 事件序列含 `tts_message` × N + `tts_end` |
| AC-05 | 合成中途断开（客户端 cancel）后**不产生缓存文件** | 中断后查目录 |
| AC-06 | 过期缓存（mtime 超 TTL）被删除并重新合成 | 改文件 mtime 后再请求 |
| AC-07 | 其他语音接口不受影响（`speech-provider` / `audio-to-text`） | 冒烟 |

## 五、影响面

- `api/internal/service/audio_service.py`（唯一改动点）
- 新增缓存目录 `storage/tts_cache/`（**不进 git**，`docker/volumes/` 已在 .gitignore）
- **无数据库变更、无接口变更、无前端变更、零新增依赖**
