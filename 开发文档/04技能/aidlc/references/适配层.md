# 适配层：六条硬规则的展开

> 本文件是 `SKILL.md` §0 的**展开**：历史背景、反例、五档审批表全文都在这里。
> **每次都要遵守的判据在 SKILL.md 里**（六条各两三行）；拿不准细节、或要写 `团队配置.md` 时再翻这里。
> 与 `references/` 其他英文原版冲突时，**本文件优先**。

## 0. 适配层：六条硬规则（优先级高于 references 内的原始要求）

遇到冲突时，以本节为准。

### A. 提问在对话里问，不要求用户去改文件

原始规则要求把问题写进 `{phase}-questions.md`，让用户自己去编辑器填。**在本环境禁止这么做。**

正确做法：
1. 用交互式提问工具（AskUserQuestion）直接在对话中提问，每题 2–5 个可选项 + 一个开放输入；
2. 拿到回答后，把「问题 + 回答 + 时间戳」**回写**到 `开发文档/<类型目录>/CR-<8位号>-<简称>/02-问题.md`；
3. 用户跳过某题时，记录 `[未答]` 并在后续按默认假设推进，同时在阶段完成消息里点明这个假设。

只有在用户主动说「给我问题清单，我自己填」时，才退化为纯文件模式。
`common/question-format-guide.md` 里的选项格式仍然要遵守（选项字母、单选、避免诱导）—— 但那份文件的
「问题必须写进 question files」一节**已作废**（文件头有说明）。
`references/` 里凡是要求「把问题写进 `{phase}-questions.md`、等用户在文件里填」的原版条款，一律按本条处理。

### B. 批准与继续是两个动作

阶段门禁提供三个选项（不要自创第四种）：

- **A. 请求修改**：用户提出意见 → 回到本阶段重做，重做后再次门禁；
- **B. 批准**：记录批准，但**不自动进入下一阶段**——等下一个角色回复「继续」；
- **C. 批准并继续**：记录批准并立即进入下一阶段（单人作业的默认选项）。

默认呈现 A/B/C。若本项目启用了 `approve-continue` 团队扩展（见第 5 节），则只呈现 A/B，
由下一角色显式说「继续」才推进。**单人项目不要开这个扩展**——批准与继续本是一步，拆开会变成自己批自己。

**若启用了 `role-gates` 扩展**：只有三个硬门（G1 需求定稿 / G2 设计定稿 / G3 代码合入）呈现门禁，
其余阶段不停，但必须报备一行「阶段｜产物｜自动通过」；发现要推翻已批准内容时立刻升级为硬门。
角色分工与身份判定读 `开发文档/00规则/团队配置.md`；找不到就问一次。

**若 `团队配置.md` 写了 `审批模式：全自动`**：本节 A/B/C 全部不适用——不呈现任何门禁，
按 `role-gates` 的「全自动模式」章节连续跑完，收尾交 `开发文档/<类型目录>/CR-<8位号>-<简称>/验收报告.md`。

**若写了 `审批模式：仅需求审批`**：只在 **G1** 呈现一次门禁（需求定稿，等你批准），
批准后 G2/G3 不生效，按全自动规则跑完；G1 未批不许进设计与构建。

#### 审批模式五档（**唯一权威表**，写进 `团队配置.md` 时按此表述）

| 档位 | 门禁行为 | 适用 |
|---|---|---|
| `全自动` | **不设门禁**；四刹车（见 §5）；收尾必须交 `验收报告.md` | 小工具 / 原型 / 试验性代码 |
| `仅需求审批` | **只留 G1**；批准后 G2/G3 不生效，按全自动规则连续跑完，同样交 `验收报告.md` | **默认**；需求要人把关、实现可托付 |
| `关键三关` | G1 需求 / G2 设计 / G3 代码合入**三处硬停**，其余阶段软通过但报备一行 | 2–3 人团队，要卡设计 |
| `每阶段` | 每个阶段结束都停 | 对外交付 / 高风险 |
| `只在交付验收` | 中间不停，最后验收一次 | 极小改动 |

**三条硬规则**

1. **档位名一字不差取自上表**。不要写「三关」「仅审需求」「只批需求」「半自动」这类变体 ——
   变体无法被程序识别，也会让下一个 agent 读不懂。
2. **`团队配置.md` 的审批模式行必须保留「五档可选：`全自动`｜`仅需求审批`｜`关键三关`｜`每阶段`｜`只在交付验收`」这段清单**，
   并保留「审批模式（五选一）」整张表。**只写当前档 = 把别人的选项藏起来了**。
   > 2026-10-26 实测：新项目初始化后 `团队配置.md` 只剩「关键三关　←　G1 需求定稿 / G2 设计定稿 / G3 代码合入三处停下等批准」，
   > 五档全丢。用户后来把档位名改成 `仅需求审批`，注释还留着三关的说法 —— **档位说不停、注释说停，互相打架**。
3. **档位与门禁表必须自洽**：`仅需求审批` 就要把 G2/G3 标成「本模式不生效」，
   `全自动` 就整表换成「无门禁」，不能让读者以为不生效的门还会停。

角色切换时，在阶段完成消息里写清「本阶段由谁批准、下一阶段该谁继续」，不要把「批准」当成「授权执行」。

### C. 审计只追加，永不覆盖

原始规则反复强调这条，但通用写文件工具默认整份覆盖，**这是最容易翻车的地方**。

- 追加方式：先 Read 读末尾 → 用 Edit 在末尾插入新条目；或直接 shell 追加
  （`cat >> 开发文档/<类型目录>/CR-<8位号>/40-审计-<人>.md`）。**一人一份**，不要写公共的 `审计.md`。
- 绝不允许「读出全文 + 拼上新内容 + 整份写回」。
- 条目必须保留用户原始输入（不概括、不改写），时间戳用 ISO 8601。

### E. 产物一律中文命名

- 根目录叫 `开发文档/`，下面**五个编号目录 + 一个汇总目录**（唯一一套布局，不再有第二种）：

  ```text
  开发文档/
  ├── 00规则/      项目概述.md  团队配置.md  协作规范.md  开发规范.md  文档结构.md
  ├── 01需求/      CR-<8位号>-<简称>/   ← 需求：用户能感知的新行为
  ├── 02缺陷/      CR-<8位号>-<简称>/   ← 缺陷：与已批准预期不符（不停 G1）
  ├── 03技术债/    CR-<8位号>-<简称>/   ← 技术债：只改内部实现（停 G1）
  │                         一条 CR 一个目录，自包含（目录名就是号）：
  │       ├── 00-状态.md          仪表盘：创建 / 更新 / 阶段 / 门禁 / 下一步
  │       ├── 01-需求.md          要什么（FR / AC）
  │       ├── 02-问题.md          缺陷类主文档（现象 / 复现 / 影响）
  │       ├── 03-前置资源.md      能不能做：缺了做不了的东西（G1 前必须列）
  │       ├── 04-风险.md          可能怎么失败 + 怎么知道它发生了
  │       ├── 05-用户故事.md      可选：多角色 / 需验收标准时
  │       ├── 06-执行计划.md      ★ 分几步做 / 改哪些文件 / 怎么验 / 不做什么
  │       ├── 07-决策记录.md      为什么这么做：选型对比 / 被否方案 / 决策人
  │       ├── 08-技术设计/            怎么设计（08-N 逐级编号）
  │       │   ├── 08-1-应用设计.md
  │       │   ├── 08-2-功能设计.md
  │       │   ├── 08-3-业务规则.md
  │       │   ├── 08-4-代码结构.md
  │       │   └── 08-5-工作单元.md
  │       ├── 20-测试记录.md
  │       ├── 21-构建说明.md
  │       ├── 30-验收报告.md
  │       ├── 31-运维说明.md      只有部署类 CR 才有
  │       ├── 32-变更说明.md      对项目级事实的影响（交付 / 存储 / 规模）
  │       ├── 40-审计-<人>.md     审计跟着 CR 走，一人一份，只追加
  │       └── 证据/               截图 / 录屏 / 样本，供验收报告引用（**不编号**）
  ├── 04技能/aidlc/            技能副本（含 scripts/ 工具；不自带副本时省略）
  └── _汇总/                   ⚙ 本地生成·**不入库**：9 个视图 + 看板.html + index.html
  ```

  **CR 内文件一律带两位编号前缀**（2026-10-27 起）。三条规则：

  1. **编号是排序位，不是「第几步」**。某份文档没有就**不建**，号**空着** ——
     绝不把后面的号往前挪。一重排，路径变、`验收报告` 里的引用断、git 历史也断。
  2. **号段留空档**：`0x` 想清楚（需求/计划/决策）｜`08` 设计（内部 `08-N`）｜
     `2x` 构建验证｜`3x` 交付｜`4x` 审计。加新文件不用挤号。
  3. **`08-技术设计/` 里超过 9 份就写两位**（`08-01-…`），否则 `08-10` 会排到 `08-2` 前面。

  > 为什么加编号：裸中文名在资源管理器里按拼音排，**跟流程阶段完全无关**。
  > 新人和 agent 打开 CR 目录，看不出先读哪个、哪个还没写。编号让「目录 = 时间线」。

  **只有五个编号目录**：设计 / 测试 / 运维 / 审计的内容都按 CR 拆进 `CR-<8位号>/`，
  全局视图由 `汇总.py` 合成到 `_汇总/`。这样两条 CR 并行时落在互不相交的路径上，**文档零冲突**。

  > **老项目不必急着迁移**：脚本查找走 `find_cr_file()`，`NN-名字.md` 与裸 `名字.md` 两种都认
  > （2026-10-27 起的软兼容）。新 CR 直接用新命名；老 CR 有空再跑
  > `scripts/迁移-编号.py <项目根>`（默认只预演，看完加 `--write` 才执行）。

- **规则文件里写的英文路径不作数**：`inception/requirements/requirements.md` 要落成
  `开发文档/01需求/CR-<8位号>-<简称>/01-需求.md`（类型目录见下节）。映射以 `references/命名对照表.md` 为唯一权威，新建文件前查表。
- **一个文件该放哪，三步判定**：① 规则/共识（不随 CR 变）→ `00规则/`；
  ② 只属某一条 CR（需求/状态/设计/测试/验收/问题/运维/变更/决策/审计）→ `<类型目录>/CR-<8位号>/`；
  ③ 跨 CR 的汇总视图 → **不手写**，跑 `汇总.py` 生成到 `_汇总/`。**没有第四步。**

  #### CR 分三类：需求 / 缺陷 / 技术债

  目录按类型分开，判据从上往下、命中即停：

  | 判据 | 类型 | 必需的主文档 |
  |---|---|---|
  | 现状与**已批准的预期不符**（本来该这样，实际不是） | **缺陷** | `02-问题.md`（现象/复现/影响） |
  | 动机是**用户能感知到的好处**（哪怕实现方式是换技术） | **需求** | `01-需求.md`（原话/范围/AC） |
  | 动机是**只有开发者能感知的好处**（可维护性 / 并行开发 / 构建速度 / 工具链），用户看到的没变 | **技术债** | `32-变更说明.md`（为什么动/影响面） |

  > **判据看「为什么要动」，不看「改了什么」。** 一句话自查：**没有这个需求，还会动这段技术吗？**
  >
  > - 会（纯粹因为代码该换了）⇒ **技术债**
  > - 不会（动了技术也只是为了让用户得到某个东西）⇒ **需求**
  >
  > | 例子 | 用户原话 | 判定 | 为什么 |
  > |---|---|---|---|
  > | `CR-26102200` | 把 localStorage 换成 IndexedDB，我要多个标签页改动能互相看到 | **需求** | 没有"多标签页同步"这个诉求就不会换存储 ⇒ 技术是手段 |
  > | `CR-16102100` | 改成 src 形式 | **技术债** | 用户界面一个像素都没变；动机是并行开发不冲突 ⇒ 只有开发者受益 |
  > | `CR-16102200` | 改成 vite 架构 | **技术债** | HMR、构建工具，用户感知不到 |

  三类**目录结构完全一样**，只有门禁不同：

  | 类型 | G1 | 理由 |
  |---|---|---|
  | 需求 | **硬停** | 范围由用户定，批准后才做 |
  | 缺陷 | **不停** | 事实清楚，不需要批准范围。但**修法有多种选择且影响用户时**（如"静默删还是二次确认"）临时升为需确认 |
  | 技术债 | **硬停** | 改的是"以后怎么干活"，属主动选择，该由人拍板 |

  **不属于任何需求的问题**（发现一个 bug 但跟当前 CR 无关）：在 `02缺陷/` 下建一条
  `not-started` 的 CR，只写 `02-问题.md`。它自然出现在状态视图的「缺陷」分组里，
  修的时候再推进状态。技术债同理。
- **技术设计写在 CR 里**：`CR-<8位号>/08-技术设计/`（`08-1-应用设计` / `08-2-功能设计` /
  `08-3-业务规则` / `08-4-代码结构` / `08-5-工作单元`）。
  目录名直说范围：只放**技术方案**，不是美术或视觉设计；视觉决策写进该 CR 的 `01-需求.md` 与代码。
- **执行计划与设计是两件事**：`06-执行计划.md` 说「分几步做、改哪些文件、怎么验」（动态路径），
  `08-技术设计/*` 说「系统长什么样」（静态结果）。两者都要，不能互相替代 —— 见 §2 开工前那一步。
- **目录带序号**是为了编辑器里顺序稳定（不带序号时按字符排，顺序不可预期）。
- 单位名用业务中文名（`工时统计`），不用英文 slug。
- **只约束文档**：代码文件名仍按语言惯例（`.ts` `.py` `.js`），不要把代码文件也中文化。
- **一律中文**：不保留英文目录，也不按阶段分目录。

### F. Git 提交：不主动提交，不整盘 add

**默认不提交。** 改完文件就停下，说清楚「改了哪几个文件、为什么」，等用户明确说「提交」再动。

提交是不可逆动作，而且最容易把「用户自己的改动」和「agent 的改动」混在一起。
用户看着工作区，比你更清楚什么时候该落盘。

| 规则 | 说明 |
|---|---|
| **禁用 `git add -A` / `git add .`** | 必须按路径精确 add。工作区里可能有用户正在改的东西 |
| **一个提交只做一件事** | 技能改造 / 需求文档 / 代码实现，分三次提交，不合并 |
| **提交前先看 `git status`** | 确认清单里没有不该出现的文件 |
| 用户明确要求时（「做完提交」「帮我 commit」） | 可以提交，但上面三条照样守 |

> **真实事故（2026-10-22）**：改完技能后习惯性 `git add -A`，把用户同时在做的整套 CR
> （`serve.py` + 两个 bat + 13 个文档，927 行）混进了「修文档」那个提交里 ——
> commit message 说的是"修取号流程"，内容九成是用户的东西。事后 `reset --soft` 才拆开。

**用户没明说时，只有这三个节点该提交**：

1. G1 批准、开始实现 —— 需求定稿该落盘
2. CR 交付 —— 代码 + 文档 + 测试记录一起
3. 用户说「验收通过」

**其余时候**：改完就停。让用户在 `git status` 里看到改动 —— 他扫一眼就知道你干了什么，
比任何 commit message 都直观。
