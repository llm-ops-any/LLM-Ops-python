# CR-16102601 决策记录

> 只记**有取舍**的决定：结论 + 理由 + 被否方案。G1 时一并确认。

## 2026-10-26 · D1 附件契约 = `files` 数组，不新增上传端点

- **背景**：Playground 打的是开放 API `/openapi/chat`，第三方也要能传文件。
- **选项**：
  1. 开放 API 新增 `POST /openapi/files`（multipart 上传，API Key 鉴权），返回 `text`/`url`
  2. 沿用现有契约：调用方自己把文件解析成 `text`，或给出可访问 `url`，放进 `files`
  3. 请求体直接收 base64 文件
- **决定**：选 **2**。
- **理由**：应用调试 / WebApp / 辅助 Agent 三处已经是这个契约，校验（`ChatAttachmentsMixin`）、上下文拼接（`build_query_with_attachments`）、落库（`build_attachment_metadata`）全现成；选 1 要在 API Key 鉴权体系里再开一条上传链路、单独做配额与清理，成本远超本次诉求；选 3 会让请求体膨胀（30MB base64 ≈ 40MB），且与 nginx `client_max_body_size 40M` 贴脸。
- **被否**：方案 1（工作量大、要新做配额/清理/鉴权）；方案 3（体积与内存风险）。

## 2026-10-26 · D2 限制值一律复用 `upload_file_entity.py` 常量

- **背景**：附件上限有 5 个 / 30MB / 单条 8000 / 总量 20000 / 落库 4000 五组数字。
- **决定**：**全部引用现有常量，前端也照抄同一组数字，不新定义、不调参**。
- **理由**：四个入口共用一条上下文注入链路，任何一处调参都会让「同样的文件在调试页能用、在 Playground 不行」；数字漂移是这类功能最常见的售后问题。
- **被否**：为 Playground 单独放宽（无诉求，且会造成行为不一致）。

## 2026-10-26 · D3 输入区保持表单，不换聊天式输入条

- **背景**：主页有 `ChatInputBar`（多行 + 附件 chip + 语音），Playground 是端点驱动的表单。
- **决定**：在「用户提问」下方加附件按钮与 chip 列表，沿用 `a-input`。
- **理由**：Playground 的价值是「端点元数据驱动」——表单、curl、快速开始文档都由 `endpoints.ts` 生成；换成聊天输入条会把它变成半个聊天页，端点切换/停止/会话清理全要重写。
- **被否**：复用 `ChatInputBar`（布局与端点驱动模型冲突，收益仅是外观）。

## 2026-10-26 · D4 不回写 `docs/Playground设计文档.md`

- **背景**：该文档是 Playground 的设计说明，但 `00规则/团队配置.md` 约定 `docs/` 下历史资料**只读**。
- **决定**：附件设计写在本 CR 的 `设计/应用设计.md`，历史文档不动。
- **理由**：历史资料一旦开始被增量修改，就会出现「一半新一半旧」且没人知道哪句有效；AIDLC 的 CR 目录本身就是新的权威。
- **被否**：直接改历史文档（违反只读约定，且无法追溯是谁什么时候改的）。

## 2026-10-26 · D5 上传走登录态、聊天走 API Key，页面文案必须写明

- **背景**：`/api/upload-files/attachment` 是 `@login_required`；Playground 的业务请求刻意 `credentials: 'omit'` 只带 API Key，以保证「结果与第三方一致」。
- **决定**：附件上传用浏览器登录态（页面本来就是登录后进入的），聊天请求维持只带 API Key；**Playground 页头说明补一句这个差异**。
- **理由**：让上传也走 API Key 需要新开鉴权分支；而差异如果不写出来，用户会以为第三方也能直接传本地文件，线上对接时才发现不行（见 `风险.md` R-04）。
- **被否**：给上传接口开 API Key 鉴权（新鉴权分支 + 配额问题，与 D1 同因被否）。

## 2026-10-26 · D6 curl 面板必须给 `files` 全文，靠折叠而非截断解决体积

- **背景**：`files` 里的 `text` 最长 100000 字符，全量进 curl 会让面板很难看。
- **决定**：curl 文本**保留全文**（保证「复制即可执行」这个承诺），面板展示层做折叠摘要。
- **理由**：截断后的 curl 是「看起来对、跑起来错」的假命令，比难看更糟。
- **被否**：curl 里截断 `text`（破坏可执行性）。

## 2026-10-26 · D7 图片附件只传地址、不做多模态解析（AC-13 降级）

- **背景**：验收实测（`测试记录.md` T9）：`files` 传 `{"kind":"image","url":"https://…/demo-arch.png"}`，
  请求 200 不报错，但模型回答「看不到图片」。根因在既有链路 `api/internal/lib/helper.py:58`
  `build_query_with_attachments()`：对无 `text` 的附件只拼「【附件信息】文件名 / 文件类型 / 文件地址」纯文本，
  **从未构造多模态 `image_url` 内容块**，图片像素不进模型。应用调试 / WebApp / 辅助 Agent 三个入口行为相同。
- **选项**：
  1. 接受现状：AC-13 降级为「`kind=image` + `url` 正确进入上下文段、不报错」，API 文档写明「当前不解析图片内容」
  2. 本 CR 扩范围：改 `helper.py` 生成 `image_url` 内容块（四处入口一并生效，需视觉模型 + 图片公网可读）
  3. 本期前端禁用图片附件，多模态另开 CR
- **决定**：选 **1**。PO 张勇 2026-10-26 在验收对话中明确选择「A. 接受现状，文档如实写明」。
- **理由**：这是四个入口共有的既有行为，不是本 CR 引入的缺陷。只在 Playground 一个入口做多模态，会让同一份附件
  在「应用调试 / WebApp / Playground」表现不一致；且方案 2 需重新过 G1 补范围、回归四条链路，成本远超本次诉求。
  本次目标是把 `files` 契约与页面入口做对，「图片能否被看懂」属于附件链路的独立议题。
- **被否**：方案 2（范围与回归面过大，且要重新定范围）；方案 3（削弱既定 Q2=A「图片+文档」结论，
  且调用方仍需要把图片地址透传给下游应用）。
- **遗留**：真多模态（`image_url` 内容块）另开 CR，届时四个入口一起改，并同步改本页文案。
