## 二、配置存储

表 `platform_setting`（KV，一行一条设置，将来加设置项不用再建表）：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | UUID PK | `uuid_generate_v4()` |
| `name` | String(255) | 唯一，本次固定 `model_provider` |
| `value` | Text | JSON 字符串：`{"base_url": "...", "api_key_cipher": "..."}` |
| `updated_at` / `created_at` | DateTime | 与既有表一致，`CURRENT_TIMESTAMP(0)` |

**为什么是 KV 而不是 `model_provider` 专用单行表**：设置项只会增加不会减少，KV 表加一项不用再写迁移；专用表在加第二个设置时必须改表结构。

**`base_url` 明文、`api_key` 密文**：地址本身不敏感，且要展示给用户看；key 必须密文。

## 三、凭证读取链路

```
ModelProviderService.get_active_config()
  ├── 进程内缓存命中（TTL 5s）→ 直接返回
  ├── 查 platform_setting(name='model_provider')
  │     ├── 有行 → 解密 api_key（失败则视为未配置并告警）
  │     └── 无行 → 回退 os.environ: OPENAI_API_BASE / OPENAI_API_KEY
  └── 写回缓存，返回 ProviderConfig(base_url, api_key, source)
```

- **TTL 5 秒**：满足「保存后 ≤10 秒生效」，又不至于每次调用打库。
- **保存时清本进程缓存**：本进程立即生效，其它 worker ≤5 秒。
- **解密失败降级**：返回 `source="env"`，不抛穿（风险 R3）。
- 读不到（app context 外 / 表未建）也降级 env，**永不因配置读失败让对话挂掉**。

## 四、凭证注入点（关键设计）

**不在 `load_language_model` 里逐个注入，而是在 `providers/uino/chat.py` 的 `__init__` 里统一补默认值。** 原因：项目里有 6 处硬编码 `Chat(model="deepseek-v4-flash", ...)`（`conversation_service` 3 处、`ai_service`、`app_service`、`assistant_agent_service`），逐处改容易漏、且以后新增一处又会绕开配置。

```python
class Chat(ChatOpenAI, BaseLanguageModel):
    def __init__(self, **kwargs):
        # 延迟导入：避免 chat.py ←→ service 包的循环导入
        from internal.service.model_provider_service import get_active_config
        cfg = get_active_config()
        if cfg.base_url and not kwargs.get("openai_api_base"):
            kwargs["openai_api_base"] = cfg.base_url
        if cfg.api_key and not kwargs.get("openai_api_key"):
            kwargs["openai_api_key"] = cfg.api_key
        super().__init__(**kwargs)
```

- 显式传参优先（`if not kwargs.get(...)`），调用方要覆盖仍然能覆盖。
- `base_url`/`api_key` 用 `openai_api_base`/`openai_api_key`（`langchain-openai==0.1.25` 的稳定字段名）。

**向量化**：`EmbeddingsService` 单例内部维护签名 `(base_url, api_key, model, dimensions)`，每次取 `embeddings` / `cache_backed_embeddings` 前比对；不一致就重建实例并重建 `CacheBackedEmbeddings`。这样改 key 后无需重启，且不破坏 Redis 缓存。

## 五、接口设计

| 方法 | 路径 | 用途 | 响应要点 |
|---|---|---|---|
| GET | `/api/model-provider` | 读当前设置 | `{base_url, has_api_key, source, provider_label}`，**无 key 字段** |
| POST | `/api/model-provider` | 保存 | body `{base_url, api_key?}`；`api_key` 空或缺失 = 不改 |
| POST | `/api/model-provider/test-connection` | 测试连接 | body `{base_url?, api_key?}`（缺省用已存值）；`{ok, status, message, model_count}` |

- 三个接口都 `@login_required`（与 `/account/*` 一致）。
- `test-connection` **不落库**，纯只读探测。
- 请求体校验用 `FlaskForm`（项目统一风格），响应掩码在 schema 的 `pre_dump` 里做。

Key 行三态：

2. **修改中**：`a-input-password`，placeholder「留空则保持不变」

保存逻辑：`api_key` 仅在「修改中且输入非空」时提交，否则不传该字段。
