# 应用设计 · 图片附件多模态输入

> 对应 `需求.md` FR-01 ~ FR-05。改动集中在「消息构造」与「Agent 对 list content 的兼容」，不动存储与前端。

## 1. 数据流（改造后）

```text
前端/第三方上传附件
  └─ kind=image, text="", url=https://...   （已由 CR-16102601 提供）
        │
        ▼
service 层（4 条链路）
  llm = load_language_model(model_config)
  supports_image = ModelFeature.IMAGE_INPUT in llm.features      ← 开关（FR-02）
  content = build_human_message_content(query, files, supports_image)
  HumanMessage(content=content)                                   ← str 或 list
        │
        ▼
FunctionCallAgent / ReACTAgent
  preset_operation：审核只看文本部分（FR-04）
  long_term_memory_recall：HumanMessage(content) 原样透传 list
  llm.stream(messages)  →  平台按 image_url 拉图  →  视觉模型读图
```

## 2. 新增：`build_human_message_content`

位置：`api/internal/lib/helper.py`（与 `build_query_with_attachments` 同文件，紧邻其定义）

```python
def build_human_message_content(
    query: str,
    attachments: Any = None,
    supports_image: bool = False,
) -> str | list[dict]:
    """构造本轮人类消息内容：模型支持图片输入且存在图片附件时返回多模态list，否则返回纯文本"""
```

判定与拼装规则：

| 条件 | 返回 |
|---|---|
| `supports_image` 为假 | `build_query_with_attachments(query, attachments)`（与改造前逐字一致） |
| 无附件 / 附件不是 list / 无「`kind=image` 且 `text` 空 且 `url` 以 `http` 开头」的项 | 同上 |
| 有图片附件 | `[{"type":"text","text": 文本段}, {"type":"image_url","image_url":{"url": u}}, ...]` |

文本段构成（保持可读、可回溯）：

```text
<query>

-----
用户随本条消息上传了 N 张图片（顺序与下方图片一致），另有 M 个附件信息如下，请结合图片与附件回答用户提问：

【图片1】<name>
【图片2】<name>

【附件1】<name>
<text 或 文件地址>
-----
```

- 非图片附件（有 `text` 的文档、无 `text` 的二进制）仍交给 `build_query_with_attachments` 处理，避免两处拼装口径分叉。
- 图片数量受 `MAX_CHAT_ATTACHMENT_COUNT` 约束；`http` 之外的 URL（如 `data:`）不进 `image_url`，降级为文本。
- 不下载、不校验图片字节：拉取由模型侧完成（`前置资源.md` P-03 已验证公网可达）。

## 4. Agent 兼容 list content

| 位置 | 现状 | 改造 | 为什么 |
|---|---|---|---|
| `function_call_agent.py::_preset_operation_node` | `query = state["messages"][-1].content`；`keyword in query` | 新增 `extract_text_content(content)`：list 时拼接各 `type == "text"` 片段 | `in` 对 list 是元素比较，list 中含 `image_url` 时敏感词永远判不中，审核被静默绕过 |
| `function_call_agent.py::_long_term_memory_recall_node` | `HumanMessage(human_message.content)` | 不动（`content` 允许 list，原样透传） | 转成字符串会丢图 |
| `react_agent.py` 对应逻辑 | 同上 | 同步改造 | 两个 Agent 共用同一套行为 |
| `model_entity.py::get_num_tokens_from_messages` | 只累加 `isinstance(content, str)` | list 时累加 `text` 片段 | 否则带图请求 token 恒按 0 计（偏低），见 `风险.md` R-04 |

`MessagesState` / `messages_to_dict` 无需改动：langchain 原生支持 list content 的序列化。

## 5. 不变量

1. `build_query_with_attachments` 行为零变化 —— 4 条链路的非视觉模型分支、以及所有落库元信息路径不受影响。
2. 无附件请求的 content 仍是纯 `str` —— 现有 `SSE` 事件、`Message` 落库、token 统计全部不变。
3. 不新增依赖、不改表结构、不改前端契约（`files` 字段形状不变）。
