# AIDLC（通用版 · 不绑定具体 IDE）

本技能是 [awslabs/aidlc-workflows](https://github.com/awslabs/aidlc-workflows) 1.x 规则集的中文通用适配版：
**规则内容原样保留**在 `references/`，只重写了本文件。

**适用于任何能读文件的编码 agent** —— Codex、Claude Code、Cursor、Windsurf、Copilot、CodeBuddy、
WorkBuddy，以及自己写的 agent。不依赖某一家 IDE 的专有机制。

- 规则细则目录：`references/`（相对本文件）。文中出现的 `inception/xxx.md`、`common/xxx.md` 等路径，
  一律指 `references/` 下的相对路径。
- 规则文件是用英文写的，**对用户说话一律用中文**；规则原文里的措辞（例如阶段完成消息模板）翻译后再呈现。

### 怎么让不同 agent 都能触发这个技能

技能是说明书，**问题是 agent 怎么知道要读它**。靠项目根的**锚点文件**（由 `install-project-anchors.py` 生成）：

- **始终写**：`AGENTS.md`（通用，最大公约数）、`CLAUDE.md`（Claude Code）；
- **项目里有对应目录才写**：`.cursor/rules/aidlc.mdc`、`.windsurf/rules/aidlc.md`、`.github/copilot-instructions.md`、
  `.trae/rules/aidlc.md`、`.codebuddy/rules/aidlc.mdc`、`.workbuddy/memory/MEMORY.md`。

**为什么不全写**（2026-10-26 定）：`~/.cursor` 装过 Cursor 不代表这个项目用 Cursor；按用户主目录探测，会在别人仓库里
造出一堆没人读的规则文件，还得挨个解释。**宁可少写，不要造死文件。** 没 python 时把
`references/project-agents.template.md` 全文复制成 `AGENTS.md`（带 `AIDLC:v2` 标记段即可），效果一样。

### 环境差异怎么处理

只描述**意图**（「读这个文件」「跑这条命令」），**不指定工具名** —— 手上有什么用什么（`Read`/`cat`、`Edit`/`sed`）。
没有 bash / python 时：脚本步骤跳过、用纯文本操作代替，视图不生成也不影响正确性（它只是加速阅读）。
**唯一不能妥协的**：审计只追加 —— 工具只能整份写文件时，先读再整份写回也会覆盖别人的记录（见规则 C）。

## 0. 适配层：六条硬规则（优先级高于 references 内的原始要求）

> 六条的**展开**（历史背景、五档审批表全文、四刹车、反例）见 `references/适配层.md`。
> 本节只留「每次都得照着做」的判据 —— 与 `references/` 里任何英文原版冲突，**以本节为准**。

**A. 提问在对话里问，不要求用户去改文件。**
直接问（每题 2–5 个具体选项 + 一个开放输入），拿到回答后把「问题 + 回答 + 时间」回写到本条 CR 的 `02-问题.md`。
**禁止**让用户去编辑 `{phase}-questions.md`。用户主动说「给我问题清单我自己填」时才退化为文件模式。

**B. 批准与继续是两个动作。**
门禁只给三选项：**A 请求修改 / B 批准（不自动进下一阶段）/ C 继续（才进）**。
「看起来没问题」不算批准，要用户明说；不要自创第四种选项。
审批模式五档（写进 `团队配置.md` 的就是这五个字，**别写「三关」「仅审需求」这类变体**）：
`全自动` ｜ `仅需求审批` ｜ `关键三关` ｜ `每阶段` ｜ `只在交付验收`。各档停哪几个门、四刹车、含义表 → `references/适配层.md`。

**C. 审计只追加，永不覆盖。**
一人一份 `<类型目录>/CR-<8位号>/40-审计-<人>.md`，只 append；**不写公共 `审计.md`**；不概括、不改写用户的原始输入。

**D. 常驻加载预算。**
启动只读三份：`common/process-overview.md`、`session-continuity.md`、`content-validation.md`。
其余一律按需读，**不要一次读完 `references/`**。本文件自己也是开销：判据留下，背景进 `references/`。

**E. 产物一律中文命名，布局只有一套。**
`开发文档/` 下五个编号目录 + `_汇总/`；一条 CR 一个自包含目录 `CR-<8位号>-<简称>/`；
**代码不进 `开发文档/`**。命名以 `references/命名对照表.md` 为唯一权威。

**F. Git：不主动提交，不整盘 add。**
改完就停，让用户在 `git status` 里看；用户要求提交时只 `git add` 本次改动的具体路径。
## 1. 启动

> **硬规则（优先级最高）**：先看工作区有没有 AIDLC 布局——判据是**任一成立**：
> `开发文档/00规则/` 存在，或任一 `<类型目录>/CR-*/` 下有 `00-状态.md`（老项目的裸名 `状态.md` 也算）。
> 有 ⇒ 这是进行中的 AIDLC 项目，**用户的任何新需求都按迭代处理**，不许问「要不要走 AIDLC」，
> 也不许因为「这次改动很小」就直接写代码。没有 ⇒ 才按新流程或普通对话处理。
>
> **不要只看项目级 `开发文档/状态.md`**：它是可选的汇总快照，可能没建、也可能被删（试点2 就没有）。
> 真实权威永远是每条 CR 的 `00-状态.md`；拿它当唯一判据，会把进行中的 AIDLC 项目误判成普通对话。
>
> 历史事故（2026-10-18，CodeBuddy）：用户只说「部署到线上，能发个链接给同事」，技能因描述缺少
> 上下文触发条件被判为不适用，直接生成代码、跳过全部门禁。本规则与新增的描述条件就是为堵这个洞。

**「微改动」的边界（AIDLC 项目里怎么处理小改动）**

不是「不走流程」，是**走最短的一条路**。四条**全满足**才算微改动：

1. 只碰 **1 个文件**、改动 **< 20 行**；
2. 不改变**用户可感知的行为**（只改文字、颜色、间距、注释、变量名）；
3. 不碰**数据、接口、构建配置、依赖版本**；
4. **看一眼就知道对不对**，不需要测试来确认。

做法：归到**当前进行中的 CR**（没有就开一条技术债 CR）→ 直接改 → `00-状态.md` 的「下一步」写一行 →
`40-审计-<人>.md` 追加一条（时间 / 改了什么 / 为什么算）。**不建** `01`/`06`/`08`，**不过门禁**。

**任一条不满足 ⇒ 正常流程**。「按钮做大」「加个字段显示」「换库升版本」「顺手把这段逻辑理一理」都不算
（分别改了行为、接口、依赖、逻辑）。判据是四条，不是「感觉小」；说不清就走正常流程。

**0. 新建项目（还没有 `开发文档/`）先跑初始化脚本 —— 只写入口文件不算初始化。**

> 2026-10-26 真实事故（uino-opc/opcapp）：用户说「初始化项目，入口用 CLAUDE.md，不要改 AGENTS」，
> agent 只生成了一个 6 KB 的 `CLAUDE.md` 就宣布完成，`开发文档/` **一个目录都没建**，
> 还得用户回头问「为什么没初始化开发文档」。根因：建布局这件事只写在散文里，漏一步不报错。

```bash
python <技能>/scripts/初始化.py <项目根> --entry claude   # 只写 CLAUDE.md，AGENTS.md 一字不动
python <技能>/scripts/初始化.py <项目根> --entry claude --full-entry   # 规范全文写进 CLAUDE.md
python <技能>/scripts/初始化.py <项目根>                  # 常规：自动探测各平台
python <技能>/scripts/初始化.py <项目根> --dry-run        # 只说要做什么
python <技能>/scripts/初始化.py <项目根> --refresh-templates  # 只把规则文件的「模板头」改成本项目格式
```

> **`--full-entry`**：默认入口文件只放一句「先读 AGENTS.md / 开发文档」的指针；
> 加了它就放**全文规范**。用于「项目自己的 AGENTS.md 不许改，AIDLC 规矩只能落在 CLAUDE.md」的场景 ——
> 否则 CLAUDE.md 里的指针会指向一个根本没有 AIDLC 段的 AGENTS.md。

| 它做什么 | 落点 |
|---|---|
| 六个编号目录 | `开发文档/{00规则,01需求,02缺陷,03技术债,04技能,_汇总}` |
| 五份规则文件（从模板**整份复制**） | `00规则/{项目概述,团队配置,开发规范,文档结构,协作规范}.md` |
| 项目级状态快照（可选） | `开发文档/状态.md`；**每条 CR 的真实状态在 `<类型目录>/CR-*/00-状态.md`** |
| 技能副本（项目自包含） | `开发文档/04技能/aidlc/` |
| 入口锚点 | 由 `--entry` 决定（见下） |
| git 钩子 + `.gitattributes` LF 保护 | `core.hooksPath` → `04技能/aidlc/scripts/hooks` |
| `_汇总/` 视图 + 自检 | 有 CR 才生成视图；自检结果直接打出来 |

**0.5 存量项目（已有代码 / 已有 `openspec/` / 已有旧版 `开发文档/`）接管 —— 按顺序，别即兴。**

**完整步骤、`--entry` 取值表、`AGENTS.md` 加固写法、多人并行与取号规则，见 `references/启动与接管.md`。**
常驻只记这五条硬规则：

1. **先骨架后迁移**：没有 `开发文档/` 就没地方迁，`接管-openspec.py` 会直接报错让你先跑初始化。
2. **`openspec/` 一个字节都不动**：接管是**复制**不是搬家，原始记录留着；删不删由人决定。
3. **历史 CR 置终态、不补施工图**：已归档的变更写 `阶段：delivered` + 门禁标「历史，未补签」。
4. **中文简称不自动翻译**：脚本给的是去前缀 slug（`environment-module`），要中文就过一遍。
5. **分片入库、视图不入库**：`<类型目录>/CR-*/NN-*.md` 要入库；`_汇总/` 整目录 gitignore。
   视图是扫分片算出来的，两条并行线各算一次必然不同，入库必冲突（实测一次合并 10 处冲突 → 0）。

   **每份产物写什么、必填字段、反例，见 `references/产物写法.md`**（9 节：执行计划 / 决策记录 /
   前置资源 / 风险 / 基线 vs 增量 / 领域补充 / 加脚本五条 / 页面形态）。常驻只记三条硬要求：

   - `06-执行计划.md`：需求定稿后、动手前写；**已开工却没有它 ⇒ 自检判错**
   - `03-前置资源.md`：G1 之前列全，`必需 + 待提供` 的项逐条摆给用户选「等 / 替代 / 缩范围」
   - `04-风险.md`：每条必须写「怎么知道它发生了」，写不出监控信号的不算风险

   **`团队配置.md` / `协作规范.md` / `文档结构.md` 的规范位置是 `开发文档/00规则/`**，只读这里、只写这里。

   **多人并行时额外一步**：读 `00规则/协作规范.md`（没有就读 `common/parallel-collaboration.md`），
   按 8 位号规则建 `<类型目录>/CR-<P><Y><MMDD><N>-<简称>/` 取号（**目录名就是号**）。详见 `common/parallel-collaboration.md`。

   > 为什么布局要写死（2026-10-21，待办清单项目）：先前允许「项目自定义布局」，结果工具和文档各认一套，
   > `汇总.py` 直接报「没有可汇总的需求目录」。**布局只有一套，代码和文档才不会打架。**
   > 若 agent 不读布局，下一轮会另造一套目录，两套结构并存比不拆更乱。

2. 新流程先向用户播报一次**执行计划**（走哪些阶段、跳过哪些、为什么），再进阶段 1。
   `common/welcome-message.md` 的原始欢迎语可以省略，用一句中文计划替代。
3. 新流程同时检查 `开发文档/00规则/` 五份规则文件（项目概述 / 团队配置 / 开发规范 / 文档结构 / 协作规范）：
   **初始化 = 整份复制模板再填空，不是「照着自己理解另写一份」** —— 模板里的表格和注释是内容，不是占位文字。
   五份各自的起稿来源、只问哪几项、缺了怎么补 → `references/启动与接管.md`。
   - `团队配置.md` **不存在** ⇒ 复制模板 → 问三件事（角色与邮箱 / 审批模式五选一 / 测试策略三选一）→ 只改这三处。
   - **已存在** ⇒ 读它，按 `git config user.email` 匹配角色；发现档位行被简写或自相矛盾 ⇒ **当场按五档表修正并告知用户**。

4. 立即在 `<类型目录>/CR-<8位号>/40-审计-<人>.md` 记录本次需求原文（规则 C）。

## 2. 三阶段路由

阶段是否执行由「项目状态 + 需求性质」决定，不要求用户记命令。**判据 ↓，细则与反例见 `references/阶段路由.md`。**

| 阶段 | 何时执行 | 规则文件 |
|---|---|---|
| 🔵 工作区检测 | 总是 | `inception/workspace-detection.md` |
| 🔵 逆向工程 | 存量项目且无逆向产物 | `inception/reverse-engineering.md` |
| 🔵 需求分析 | 总是（深度按 minimal/standard/comprehensive 自适应） | `inception/requirements-analysis.md` |
| 🔵 用户故事 | 影响最终用户 / 多角色 / 需验收标准 | `inception/user-stories.md` |
| 🔵 工作流规划 | 总是 | `inception/workflow-planning.md` |
| 🔵 应用设计 | 需新组件 / 服务层 / 接口定义 | `inception/application-design.md` |
| 🔵 单元拆分 | 需拆成多个工作单元 | `inception/units-generation.md` |
| 🔵 **执行计划** | **需求定稿后总是**（进构建前必须有 `06-执行计划.md`） | `references/执行计划.template.md` |
| 🟢 功能设计 | 新数据模型 / 复杂业务规则 | `construction/functional-design.md` |
| 🟢 NFR 需求 → NFR 设计 | 有性能 / 安全 / 扩展性 / 选型 | `construction/nfr-requirements.md` |
| 🟢 基础设施设计 | 涉及部署架构 / 云资源 | `construction/infrastructure-design.md` |
| 🟢 **代码生成** | **每个单元总是**（先计划 → 批准 → 生成） | `construction/code-generation.md` |
| 🟢 **构建与测试** | 全部单元完成后 | `construction/build-and-test.md` |
| 🟡 运维 | 占位，不产出实际运维动作 | `operations/operations.md` |

**测试策略三档**（写在 `团队配置.md`；**档位由用户定，agent 不得按改动类型自行升档**）：
`全量`（新增用例 + 全量回归 + 人工走查）｜`仅回归`（不新增，但跑既有全部）｜`仅静态`（只做**语法校验 + 人工测试**，不执行任何命令）。

- `仅静态` 下「构建命令」**必须留空**（钩子读到非空就会在合并后执行它），并**禁止**写「构建通过 / 测试通过」——
  没跑就是没跑，只能写「语法校验通过（未执行命令）+ 人工测试结论」。
- 降档必须留痕：`验收报告.md` 写明「本轮策略＝仅静态，未做自动化测试」+ **因此未覆盖的风险**。
- 档位标签必须与实际动作一致：新增了用例就记 `全量`；写「仅回归」却新增用例属**记录失真**。
- 三档的准入条件（三条全满足才能降）、四条硬约束的历史由来 → `references/阶段路由.md`。

> **⚠️ 部署 / 上线不是例外。** 「运维阶段是占位」≠「部署请求可以不进流程」。用户说「部署到线上」「发个链接给同事」时，
> 它仍然是一次**变更请求**：登记 CR、补部署增量（目标 / 访问方式 / 数据影响 / 回滚）、按审批模式过门禁、写审计。
> **禁止**跳过这些直接生成 `.deploy/` 脚本或 `dist/`。
> （2026-10-18 事故：用户只说「部署到线上，能发个链接给同事」，AI 直接产出脚本与 `dist/`，审计、CR、门禁三样全无。）

## 3. 每个阶段的固定动作

```
进入阶段
  → role-gates 启用时先查本条 CR 的 00-状态.md「门禁」段（前置门未 approved 不许进）
  → 只读对应规则文件 → 在 40-审计-<人>.md 记录阶段开始 → 按规则执行（提问走规则 A）
  → 产出写入 开发文档/（中文命名）→ 更新 00-状态.md（执行/跳过、当前阶段）
  → 呈现阶段完成消息 + 门禁三选项（规则 B）→ 按 A 重做 / B 等「继续」/ C 进下一阶段 → 记录用户原始回答（规则 C）
```

**不要自行发明导航选项**（原规则明确禁止 3 选项以上的「涌现行为」）。除了 A/B/C 门禁，
不要在阶段之间插入「你想先看哪个」之类的自由菜单。

## 4. 产物目录（中文命名）

写在**用户项目**里，不是技能目录。**目录名、文档文件名一律用中文**，完整对照见 `references/命名对照表.md`。

```text
<项目根>/
├── [应用代码]                # 代码在这里，按各语言惯例，不要中文化
├── AGENTS.md                 # 入口锚点（必须留在根）
└── 开发文档/                 # 只放文档
    ├── 00规则/               # 项目概述 / 团队配置 / 协作规范 / 开发规范 / 文档结构
    ├── 01需求/ 02缺陷/ 03技术债/    # 三类 CR，结构相同、门禁不同
    │   └── CR-<8位号>-<简称>/   # 一条 CR 一个目录，自包含（目录名就是号）
    ├── 04技能/aidlc/         # 技能副本（含 scripts/）
    └── _汇总/⚙               # 9 个视图 + 看板.html + index.html，本地生成、不入库
```

**没有独立的设计 / 测试 / 运维 / 审计目录** —— 都按 CR 拆进 `CR-<8位号>/`，全局视图由 `汇总.py` 合成。
`CR-<8位号>/` 里的文件（**数字前缀 = 阅读顺序**；没有的那份就不建，**号空着，绝不往前挪**）：

| 号 | 文件 | 作用 |
|---|---|---|
| 00 | `00-状态.md` | 仪表盘：创建/更新/阶段/门禁/下一步（脚本读它生成汇总） |
| 01 | `01-需求.md` | 要什么（FR / AC） |
| 02 | `02-问题.md` | 缺陷类主文档（现象 / 复现 / 影响） |
| 03 | `03-前置资源.md` | 缺了做不了的东西（G1 前必列） |
| 04 | `04-风险.md` | 可能怎么失败 + 触发信号 |
| 05 | `05-用户故事.md` | 可选：多角色 / 需验收标准 |
| 06 | `06-执行计划.md` | **分几步、改哪些文件、怎么验、不做什么** |
| 07 | `07-决策记录.md` | 为什么这么做（选型 / 被否方案 / 决策人） |
| 08 | `08-技术设计/` | 08-1 应用 / 08-2 功能 / 08-3 业务规则 / 08-4 代码结构 / 08-5 工作单元 |
| 20 | `20-测试记录.md` | 测了什么、结果、未覆盖的风险 |
| 21 | `21-构建说明.md` | 怎么构建 / 产物在哪 |
| 30 | `30-验收报告.md` | 做完了，结论 + 证据 |
| 31 | `31-运维说明.md` | 只有部署类 CR |
| 32 | `32-变更说明.md` | 对项目级事实的影响 |
| 40 | `40-审计-<人>.md` | 一人一份，只追加 |
| — | `证据/` | 截图 / 录屏 / 样本，不编号 |

`{单元}` 用业务名（`工时统计`），不要英文 slug。**代码不进 `开发文档/`**，这里也不放可执行文件；是否入库由用户定（默认建议纳入）。

**`00-状态.md` 的字段名必须是中文**（`汇总.py` / `自检.py` 按字段名解析，改名后视图就是一列 `—`），
字段**值**里的阶段名用英文标识。模板（10 个字段 + 门禁明细表）见 `references/产物写法.md` 的「状态文件」一节。

## 5. 扩展

> **落点换算（对 `references/` 全域生效）**：规则原文里的 `aidlc-state.md` / `aidlc-docs/` 等英文落点，
> 一律按 `references/命名对照表.md` 映射 —— 即**每条 CR 的 `00-状态.md`** 与 `开发文档/`。
> 规则原文不改（它是上游 1.x 的对照基准），但 agent 动手时只认本文件与对照表的中文落点。

启动时**递归扫描** `references/extensions/**/*.opt-in.md`，只读这些轻量文件、**不读完整规则**；把每个 opt-in 问题
在需求分析阶段问用户（规则 A），答案写进 `00规则/团队配置.md` 的「扩展配置」表（**项目级，写一次对所有 CR 生效**）。

- 选「用」→ 到对应阶段才读完整规则（同名去掉 `.opt-in`）；选「不用」→ 完整规则永不进上下文；
- **没有 `.opt-in.md` 的扩展视为常开**；启用的扩展是**硬约束**，不适用的规则在阶段完成消息里标 N/A（不算违规）。

| 扩展 | 作用 |
|---|---|
| `team/role-gates` | 角色门禁：停几处由档位决定，含 PO/DEV/REV 四眼原则 |
| `team/approve-continue` | 批准与继续分两步（**单人场景不要开**：自己批给自己再等自己说继续，纯增摩擦） |
| `team/audit-signature` | 审计记录带 `User` / `Email`（取 `git config`） |
| `team/doc-sync` | 代码改动后强制回写受影响的阶段文档 |
| `security/baseline` | 安全基线（鉴权、密钥、输入校验） |
| `testing/property-based` | 基于属性的测试，防 AI 改代码迁就测试 |

**新建项目先选一个预设，别逐项调**（单人 / 2–3 人 / 严格 / 全自动 / 极小改动）。落盘的必须是**档位名本身**，
与 §0-B 五档**一字不差**（别写「单人模式」「三关预设」，下一个 agent 认不出来）。
预设对照表、`全自动` 的四刹车与 `仅需求审批` 的完整行为 → `references/扩展配置.md`。

## 6. 工具（`scripts/`）

九个工具，**跟着技能走，项目里不用另建 `工具/`**；完整参数、行为、坑见 `references/工具手册.md`。
**单文件 ≤ 25 KB**（`SKILL.md` 自己也在内）—— 超了就拆，规矩见 `references/产物写法.md` 的「给技能加脚本时的六条」；
唯一例外是 `assets/docsify.min.js`（第三方压缩库，拆开跑不了）。

| 什么时候用 | 跑哪个 |
|---|---|
| 新项目开工 / 存量项目补人 | `初始化.py`（`--refresh-team` 只追加人，**已有人编号不动**） |
| 状态 / 索引 / 看板要更新 | `汇总.py`（顺带出 `看板.html`；加 `--site` 连文档站一起出） |
| 体检这个项目 | `自检.py`（18 类，清单见脚本 docstring） |
| **改完脚本先自证** | `自测.py`（临时目录跑完整闭环，别拿真实项目当测试环境） |
| 存量 OpenSpec / 老 CR 要接管 | `接管-openspec.py` / `迁移-编号.py`（**都默认只预演**，`--write` 才动手） |
| 装钩子 / 建离线文档站 | `安装钩子.py` / `预览.py`（`--no-serve` 只生成不起服务） |

**钩子只做两件事**：重建 `_汇总/` 视图；若 `团队配置.md` 声明了 `- 构建命令：xxx`，再执行它 —— **技能不猜构建命令**，
项目说做什么就做什么（否则 git 会把产物"自动合并"成半对半错，还不报冲突）。
## 7. 规则文件索引（`references/`）

**别按目录翻，按场景查**：

| 你现在要做什么 | 读这个 |
|---|---|
| 判断某阶段该不该跑 / 改测试策略 | `阶段路由.md` |
| 写某份产物（需求 / 计划 / 设计 / 风险…） | `产物写法.md`（含 `00-状态.md` 模板） |
| 新建项目 / 存量接管 / 多人取号 | `启动与接管.md` |
| 选审批模式 / 挑扩展预设 | `适配层.md`、`扩展配置.md` |
| 跑脚本、或它报错了 | `工具手册.md` |
| 中文名怎么落盘 | `命名对照表.md` |
| 初始化收尾自检 | `初始化自检清单.md` |
| 阶段内的原始规则（英文原版） | `inception/` `construction/` `operations/` `common/` `extensions/` |
| 各项模板（项目概述 / 团队 / 规范 / 结构 / 协作 / 执行计划） | `*.template.md` |

英文原版的文件名与阶段名一一对应，按 §2 阶段表第三列取；**不要一次性读完**。
`references/` 里凡要求「把问题写进 question files」的原版条款一律作废（见规则 A）。


## 8. 绝对不要做的四件事

1. 不要在没读完对应规则文件的情况下执行某个阶段；
2. 不要在用户没有明确批准时进入下一阶段（「看起来没问题」不算批准，要用户明说）；
3. 不要覆盖审计文件，也不要概括用户的原始输入；
4. 不要把应用代码写进 `开发文档/`。
