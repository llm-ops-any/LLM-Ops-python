## 1. 一句话认识这个项目

一个**类 Dify 的「AI 应用开发平台」**：用户在网页上创建 AI 应用 → 编排提示词 / 挂工具与知识库 → 调试 → 发布成 **WebApp**（对外链接）或**开放 API**（给第三方程序调）。

平台自身还带：**工作流编排**（可视化拖拽 8 类节点）、**知识库 RAG**、**模型供应商管理**、**内置应用与插件广场**。

## 2. 运行时形态（7 个容器）

编排文件 `docker/docker-compose.yaml`（全部服务都在同一 Docker 网络里）：

| 容器 | 镜像 | 宿主端口 | 职责 |
|---|---|---|---|
| `llmops-nginx` | `nginx:latest` | **80** | **唯一对外入口**，反代 ui 与 api |
| `llmops-ui` | `llmops-ui:0.1.0` | `127.0.0.1:3000` | 前端（Vite 构建产物） |
| `llmops-api` | `llmops-api:0.1.0` | `127.0.0.1:5001` | Flask + gunicorn（4 worker × 4 线程），启动时**负责跑 alembic 迁移** |
| `llmops-celery` | **同 api 镜像** | 无 | Celery worker（4 并发），处理文档索引等异步任务 |
| `llmops-db` | `postgres:15-alpine` | `127.0.0.1:5432` | 业务库 `llmops` |
| `llmops-redis` | `redis:6-alpine` | `127.0.0.1:6379` | 缓存 / Celery broker（`db=1`）/ Agent 队列停止标记 |
| `llmops-weaviate` | `semitechnologies/weaviate:1.28.4` | `127.0.0.1:8080`、`50051` | 向量库（collection `Dataset`） |

几个要点：

- **api 与 celery 是同一个镜像**，靠环境变量 `MODE`（`api` / `celery`）在 `docker/entrypoint.sh` 里分流；迁移只由 api 跑（`MIGRATION_ENABLED=true`，celery 为 `false`），避免重复执行。
- `depends_on` 带 healthcheck：api/celery 等 db、redis 健康后才启动。
- Weaviate 关掉了匿名访问、开了 API Key 鉴权，且**向量化模块设为 `none`**（`DEFAULT_VECTORIZER_MODULE: 'none'`）—— 向量由应用侧算好再写入。
- 所有数据落在 `docker/volumes/`（`db/data`、`redis/data`、`weaviate/`、`app/storage`），**清目录＝清数据**。
- 对外只暴露 80，其余都绑在 `127.0.0.1`，属于本机自用部署。

## 4. 后端架构

### 4.1 启动流程

`api/app/http/app.py`：

1. `load_dotenv()` 读 `.env` → `Config()` 组装配置（环境变量优先，缺省回退 `default_config.py`）；
2. `Http(...)` 创建应用 —— 真正的装配在 `internal/server/http.py` 的 `class Http(Flask)`：
   - `config.from_object(conf)` 应用配置；
   - 注册全局异常处理器（把 `CustomException` 的 `code` / `message` 提取成统一响应）；
   - 初始化扩展：`db / weaviate / migrate / redis / celery / logging / login_manager`；
   - **`login_manager.request_loader(middleware.request_loader)`** ← 鉴权入口，见 6.3；
   - `router.register_router(self)` 注册蓝图。
3. `app.extensions["celery"]` 取出 Celery 实例（worker 用 `celery -A app.http.app.celery worker` 启动）。

依赖注入用 `injector`：`app/http/module.py` 的 `ExtensionModule` 把 5 个扩展绑成单例，服务类里用 `injector.get(...)` 或装饰器取用。

- `openapi`（`url_prefix=""`）—— 开放 API，**鉴权方式不同**（见 6.3）。

### 5.4 请求封装（`src/utils/request.ts`）★ 改请求相关必看

四个函数，边界各不相同：

| 函数 | 机制 | 注意 |
|---|---|---|
| `baseFetch` | 从 credential 取 token 写 `Authorization: Bearer`；URL = `apiPrefix + url`；GET 拼 query，`body` 走 `JSON.stringify`；`Promise.race` 做 **100 秒超时** | **业务错误码在这里统一处理**（见下） |
| `ssePost` | POST 流式，同样注入 Bearer token | 响应是 `application/json` 时**直接 return JSON**（出错分支）；**不做错误码跳转**，所以流式接口的 401 不会踢人 |
| `handleStream` | `getReader()` + `TextDecoder` 按行解析，累积 `event:` / `data:`，**空行且两者齐全**才回调 `onData({event, data})` | 逐 token 的 `agent_message` 会多次回调，**由调用方自己累加** |
| `upload` | 基于 `XMLHttpRequest`（能报进度）；`withCredentials: true`；`FormData` | 同样按错误码判断，`unauthorized` 会清凭证跳登录 |

⚠️ **错误码判定看的是响应 json 的 `code`（字符串），不是 HTTP 状态码**：
`unauthorized` → 清凭证 + 跳登录；`notFound` → 跳 404；`forbidden` → 跳 403；其它非 success → `Message.error` + reject。

⚠️ `ssePost` 里的 `options.headers` 与 `baseFetchOptions.headers` **是同一个 `Headers` 实例**（浅拷贝而来），所以**不能拿它去发「用其它凭证」的请求** —— 会互相污染。

### 5.5 stores 与配置

- **只有 2 个 Pinia store**：`account`（账号信息）、`credential`（`access_token` + `expire_at`），都持久化到 localStorage；
- `src/config/index.ts`：`apiPrefix`（来自 `import.meta.env.VITE_API_PREFIX`）、`httpCode`（**6 个字符串枚举**：`success` / `fail` / `not_found` / `unauthorized` / `forbidden` / `validate_error`）、`typeMap`（工具参数类型中文名）、`QueueEvent`（Agent 的 SSE 事件名常量）；
- 环境变量三件套：`.env`（通用项）、`.env.development`（`VITE_API_PREFIX=http://localhost:5001` **直连后端**）、`.env.production`（`VITE_API_PREFIX=/api` 走 nginx）；
- `vite.config.ts` 只有 `vue()` 插件 + `@` 别名，**没有 `server.proxy`** —— 开发态靠 `.env.development` 的绝对地址直连 5001。

## 6. 核心业务链路（重点）

> 本章六小节：6.1 应用与配置版本 → 6.2 对话链路 → 6.3 开放 API 链路 → 6.4 RAG → 6.5 工作流 → 6.6 模型加载。

### 6.1 应用与配置版本机制

核心是**「草稿配置」与「已发布配置」分离**：

| 表 | 角色 |
|---|---|
| `app` | 应用基本信息，`draft_app_config_id` 指向当前草稿 |
| `app_config_version` | **草稿 / 版本历史** |
| `app_config` | **已发布生效的配置** |
| `app_dataset_join` | 应用 ↔ 知识库的关联 |

两条链路取配置的方式不同，这是最容易踩的点：

- **调试走草稿**：`app_service.debug_chat` 用 `get_draft_app_config` → 改了配置**不用发布**就能立刻调试；
- **开放 API 走已发布**：`openapi_service.chat` 校验 `app.status == PUBLISHED` 后取运行时配置 → **不发布就调不通**。

### 6.2 对话链路（内部调试）

调用链（`→` 表示调用）：

```
前端 POST /apps/<app_id>/conversations          router.py
  → app_handler.debug_chat                      handler 层，@login_required
    → app_service.debug_chat                    service 层（普通实例方法）
      · get_app() + get_draft_app_config()      取草稿配置
      · conversation = app.debug_conversation   用固定的调试会话
      · load_language_model(...)                取 LLM 实例
      · 构造 AgentConfig(invoke_from=DEBUGGER, user_id=account.id)
      · 按 llm.features 选 FunctionCallAgent 或 ReACTAgent
      · for thought in agent.stream({...})      消费 Agent 产出的事件
  → 转成 SSE（text/event-stream）返回前端
```

**「流式」是怎么实现的**（`core/agent/agents/base_agent.py` 的 `stream()`）：
**开一个子线程跑 Agent 图**，HTTP 请求线程在**进程内内存队列**上取事件 —— 理解流式与停止机制的关键就在这。

**队列与 Redis 键**（`core/agent/agents/agent_queue_manager.py`）：

| Key | 内容 | TTL |
|---|---|---|
| `generate_task_belong:{task_id}` | 任务归属（`{user_prefix}-{user_id}`） | 1800s |
| `generate_task_stopped:{task_id}` | 停止标记 | 600s |

- `publish(task_id, thought)`：把事件 `put` 进队列；遇到 `STOP` / `ERROR` / `TIMEOUT` / `AGENT_END` 时调 `stop_listen()` 收尾；
- `listen(task_id)`：循环从队列 `get(timeout=1)`，取到 `None` 即结束；每 **10 秒**发一次 `PING` 心跳；**600 秒**无事件发 `TIMEOUT`；每轮检查停止标记；
- `stop_listen()`：往队列 `put(None)` 让 `listen` 退出。

**停止机制（三步）**：

1. 前端 `POST /apps/<app_id>/conversations/tasks/<task_id>/stop`；
2. `AgentQueueManager.set_stop_flag(task_id, InvokeFrom.DEBUGGER, account.id)` —— 它是 **classmethod**，先校验 `generate_task_belong` 的归属键**匹配**，通过才写 `generate_task_stopped:{task_id}`；
3. `listen()` 循环发现停止标记 → `publish(STOP)` → `stop_listen()` → 生成器结束 → SSE 流终止。

> 注意一个设计要点：**事件走内存队列（同进程内），只有停止标记走 Redis（跨进程）** —— 因为「停止」请求可能落在另一个 gunicorn worker 进程上，必须靠 Redis 传话。

### 6.3 开放 API 链路，以及它与调试链路的差异 ★

鉴权入口是 `internal/middleware/middleware.py` 的 `request_loader`，**按蓝图分流**：

```
request.blueprint == "llmops"    → 用 access_token（JWT）换账号
request.blueprint == "openapi"   → 用 Authorization: Bearer <api_key> 查 api_keys 表换账号
```

→ 所以**第三方只要带 API Key，不需要登录态**；反过来，**调开放 API 时绝不能带 `access_token`**（后端会拿 JWT 字符串去 `api_keys` 表查，必然报「该秘钥不存在或未激活」）。

两条链路的差异对比：

| 维度 | 内部调试 `debug_chat` | 开放 API `chat` |
|---|---|---|
| 端点 | `POST /apps/<app_id>/conversations` | `POST /openapi/chat` |
| 鉴权 | 登录态 JWT | API Key |
| 取哪套应用配置 | **草稿**（`get_draft_app_config`） | **已发布**（校验 `app.status == PUBLISHED`） |
| 会话主体 | 固定的调试会话 | `end_user`：传了 `end_user_id` 就校验归属，否则新建 |
| `conversation` / `message` 上的 `invoke_from` | `DEBUGGER` | `SERVICE_API` |
| **`AgentConfig` 的 `invoke_from` / `user_id`** | `DEBUGGER` / `account.id` | **`DEBUGGER` / `account.id`** ⚠️ |
| 停止接口 | 有 | 无 |

⚠️ **最后两行是重点，也是一个「疑似遗留」**：开放 API 在**会话与消息**上用的是 `SERVICE_API` + `end_user.id`（语义正确 —— 这是外部调用，主体是终端用户），但在**构造 `AgentConfig` 时写成了 `DEBUGGER` + `account.id`**（`openapi_service.py` 约 L141-142），大概率是复制调试链路时留下的。

它带来的实际影响：`AgentQueueManager` 判断 `user_prefix` 时，`DEBUGGER` 落在「按账号维度」那一档，于是**开放 API 的任务归属键是 `account-{account_id}`**：

- 好处：新增停止端点时可以**仅凭 API Key 就完成归属校验**，无需额外参数；
- 代价：它与「应用调试页面」的任务共享同一命名空间，同账号内无法区分。

### 6.4 RAG（知识库）链路

**写入链路** —— `IndexingService.build_documents`（由 Celery 任务触发），四个阶段：

| 阶段 | 做什么 |
|---|---|
| `_parsing` | `FileExtractor.load()` 把上传文件解析成 LangChain `Document` |
| `_splitting` | 按文档的 `process_rule` 选切分器切分，**每段建一条 `Segment` 行**（`node_id=uuid4`，状态 WAITING），并把 `account/dataset/document/segment/node_id` 写进 metadata |
| `_indexing` | 结巴提取关键词（最多 10 个），维护 `KeywordTable` |
| `_completed` | 每 10 条一批调 `vector_store.add_documents(chunks, ids=node_id)` **写进 Weaviate**，分段置 COMPLETED |

> 向量化不是显式调的：`WeaviateVectorStore` 注入的是 `embeddings_service.cache_backed_embeddings`（`OpenAIEmbeddings` + `CacheBackedEmbeddings` 套 Redis 缓存），写库时由向量库内部回调完成。

**检索链路** —— `RetrievalService.search_in_datasets`：

- 同时建 `SemanticRetriever`（语义：`similarity_search_with_relevance_scores`，用 `Filter` 过滤 `dataset_id` / `document_enabled` / `segment_enabled`）与 `FullTextRetriever`（结巴关键词 → 查 `KeywordTable` → 命中计数排序）；
- 再组 `EnsembleRetriever(weights=[0.5, 0.5])`，按策略分派 `SEMANTIC` / `FULL_TEXT` / hybrid；
- 每次检索写一条 `DatasetQuery`，并给命中的分段 `hit_count + 1`。

**检索结果怎么进入提示词（两种场景，别混）**：

- **对话场景**：检索被包成一个叫 `dataset_retrieval` 的 LangChain 工具，结果用 `combine_documents` 拼成字符串返回 → **作为 `ToolMessage` 回到 Agent 循环**，由 Agent 框架带入下一轮 LLM 上下文。即：**知识库在对话里是「工具」，不是「前置注入」**；
- **工作流场景**：`DatasetRetrievalNode` 调同一套检索，结果作为**节点 output**，由下游 LLM 节点用 jinja2 模板引用。

**关键参数与库**：

- Weaviate collection 名 `Dataset`，文本属性 `text`；记录主键 = segment 的 `node_id`；
- embedding 实际用 `qwen3-embedding-8b` + `EMBEDDINGS_DIMENSIONS=1536`（代码兜底默认是 `text-embedding-3-small`）；**1536 维必须与辅助 Agent 预置的本地 FAISS 索引对齐**；
- 另有一条独立支线：`FaissService` 加载 `core/vector_store/index.faiss`，只给**辅助 Agent** 用（与 Weaviate 无关）。

### 6.5 工作流链路

- **存储**：`workflow` 表存 `draft_graph`（草稿）与 `graph`（已发布）+ `is_debug_passed` + `status`；`workflow_result` 表存每次运行结果（`graph` / `state` / `latency` / `status`，`app_id` 为空表示非应用调用）；
- **草稿 → 发布**：改草稿会把 `is_debug_passed` 置 False；**必须先调试通过**，`publish_workflow` 才允许把 `draft_graph` 复制成 `graph` 并置 PUBLISHED；取消发布则清空 `graph`、退回 DRAFT；
- **8 类节点**：`start` / `end` / `llm` / `template_transform` / `dataset_retrieval` / `code` / `tool` / `http_request`，都继承 `core/workflow/nodes/base_node.py` 的 `BaseNode`，实现 `invoke(state, config) → WorkflowState`；
- **执行引擎**：`core/workflow/workflow.py` 的 `class Workflow(BaseTool)` 用 **LangGraph** 的 `StateGraph(WorkflowState)`，逐节点 `add_node`、逐边 `add_edge`，起点 START / 终点 END，最后 `compile()`；
- **是流式的**：`Workflow.stream()` 逐节点 yield，服务层转成 SSE 返回。

### 6.6 LLM 供应商与模型加载

**三层配合**（本项目最「配置化」的一块）：

| 层 | 文件 | 作用 |
|---|---|---|
| 供应商元信息 | `core/language_model/providers/providers.yaml` | 声明有哪些供应商（名称、图标、支持的模型类型） |
| 供应商实现 | `providers/<name>/chat.py` | 真正的 LangChain 模型类（按 `supported_model_types` 动态导入，`chat` → Chat 类） |
| 模型清单与参数 | `providers/<name>/positions.yaml` + `providers/<name>/<model>.yaml` | 列出模型名，并逐个定义参数 |

**加载路径**：`LanguageModelService.load_language_model(model_config)` → 取 `provider` / `model` / `parameters` → `manager.get_provider()` → `provider.get_model_entity()` → `provider.get_model_class()` → `model_class(**模型YAML属性, **用户参数, features=..., metadata=...)`。失败会兜底到默认模型（默认 `uino` / `deepseek-v4-flash`，可用 `DEFAULT_LLM_PROVIDER` / `DEFAULT_LLM_MODEL` 覆盖）。

**调用点**：应用对话、WebApp、开放 API、工作流的 LLM 节点 —— 全部走这一个方法。

**参数默认值**在 `core/language_model/entities/default_model_parameter_template.py`（`temperature` 默认 1、`top_p` 默认 **0**、`max_tokens` 默认 None…）；模型 YAML 的 `parameters` 覆盖它，运行时用户参数再覆盖。

**供应商目录（6 个）**：`uino` / `openai` / `tongyi` / `wenxin` / `moonshot` / `ollama`。

`uino` 是本项目**自定义新增**的（其余是 LangChain 官方内置的封装），结构与其它供应商完全一致（`chat.py` + `positions.yaml` + 模型 YAML + 图标），但有三处特殊：

1. 继承 `ChatOpenAI`（走 OpenAI 兼容协议），接口地址与密钥复用 `OPENAI_API_BASE` / `OPENAI_API_KEY`；
2. 重写 `get_num_tokens_from_messages`，绕开 tiktoken 不认识第三方模型名的问题；
3. 模型 YAML 里带 `extra_body.thinking.type=disabled` —— **关掉 deepseek 的思考模式**，否则「流式 + 工具调用」会随机 400。
