# 决策记录

> **整份复制**到 `开发文档/<类型目录>/CR-<8位号>-<简称>/07-决策记录.md` 再填。
> 时机：**做决定的同时写**，不是收尾时回忆。
>
> 只在**有取舍**时写。没有备选方案的事不用记（"加个按钮"不需要决策记录）。
> 反过来说：**被否掉的方案尤其要记** —— 半年后有人问"当初为什么不直接用现成的 X"，答案在这里。

---

## 什么时候必须写

| 场景 | 例子 |
|---|---|
| 两条以上路都能走通，选了其中一条 | 固定 up ／ 旋转底板 180° ／ 改 layout direction |
| 保留了看起来"不对"的现有行为 | "这条规则违反直觉，但改它会连带影响 X，所以保留" |
| 违反 AIDLC 默认约定 | 跳过 G1、缺陷类不建 `01-需求.md`、`仅静态` 不跑构建 |
| 参数取值靠估 | `fitMargin` 1.28、后退倍率 1.15 —— 凭什么取这个数 |
| 用户明确否掉了某个方案 | **必记**，否则下一轮会重新提一遍 |

## 什么时候不用写

- 只有一条路可走（"按规范加个字段"）。
- 用户当场拍板的纯执行项。
- 具体到某行代码怎么写 —— 那是实现，`git diff` 已经记了。

---

## 单条格式（五要素，缺一不可）

```markdown
## D-01 保存视角分支的滚转基准（2026-10-30）

- 背景：功能设计第 2 条写的是「恢复进入前的 up 方向」，实测在正俯视时会造成 180° 翻转。
- 选项：（可选，但有多方案时必填）
- 决定：保存视角分支的 up 固定取 GraphLayout.camera.upDirection（[0,0,1]）。
- 理由：保存数据只有 position/target，滚转只能由 up 决定；固定后不依赖进入前相机状态。
- 被否：① 换成 [0,0,-1] —— 把错误结果当正确结果，倾斜视角仍错；
        ② 旋转整个底板 180° —— 会连带改掉同屏、点位生成与布局数据。
- 影响：退出逻辑空间仍按 _lockCamera 采集值还原，_unlockCamera 未改。
```

| 要素 | 写什么 | 常见错法 |
|---|---|---|
| 背景 | 为什么需要决策（冲突 / 约束 / 反例） | 抄需求原文 |
| 决定 | **选了什么**，一句话 | 写成"分析了三个方案" |
| 理由 | 凭什么选它 | 写"综合考虑" |
| 被否 | 落选方案 + **落选原因** | 只列方案名不写为什么否 |
| 影响 | 这个决定约束了后面什么 | 省略（下一个接手的人会重复踩） |

## 编号与追加规则

- 编号 `D-01`、`D-02`… 按时间递增，**不重号、不改号**。
- 后续轮次推翻前面某条时：**不修改原条目**，新开一条，并在原条目下加一行
  `> 已被 D-0N 取代（YYYY-MM-DD）：原因…`
- 参数类决策（倍数、阈值、超时）要把**取值**写进「决定」，不要只写"适当调大"。
