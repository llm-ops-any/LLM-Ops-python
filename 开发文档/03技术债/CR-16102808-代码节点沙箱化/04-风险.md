# CR-16102808 风险

| # | 风险 | 可能性 | 影响 | 触发信号 | 应对 |
|---|---|---|---|---|---|
| **R-01** | 白名单误伤现有工作流（用了未放行的模块） | 中 | 已有流程突然跑不通 | 用户报「模块 xxx 不允许导入」 | 上线前 grep 全部 workflow 的 code 节点做清单核对；已确认当前唯一一个只用 `json/hashlib/base64` |
| **R-02** | 每次起进程导致节点变慢 | 低 | 工作流整体延迟 +30~80ms | 压测对比 | `-S` 跳 site 导入；实测后若 >200ms 再考虑常驻进程池 |
| **R-03** | **fork 炸弹残留子进程** | 低 | 容器内进程数暴涨 | `ps` 看到大量 python 进程 | 超时后 `os.killpg(SIGKILL)` 杀进程组；root 不受 NPROC 限制（D-05），需人工核实；监控容器进程数 |
| **R-04** | **仍能读文件系统**（如读 `.env`） | **中** | 拿到数据库密码等 | 构造 `open('/app/api/.env')` 测试 | L4 拦截 `open`；但绕过 L4 后仍可读。**这是本 CR 明确不解决的残留风险**（见需求 §三.3），要彻底解决需容器级隔离 |
| **R-05** | 子进程里 `print` 到 stdout 污染结果 JSON | 中 | 解析失败 | 用户代码里有 `print` | runner 用固定分隔标记或把结果走 fd 3；本次用「最后一行是 JSON」约定，并在 runner 里重定向 stdout |
| **R-06** | 合法代码被 `getattr` 禁用波及 | 低 | 少数动态写法报错 | 用户报「不允许调用 getattr」 | 提示里说明原因；确有需要再评估放开 |
| **R-07** | `preexec_fn` 在多线程进程里有风险 | 低 | 偶发死锁 | gunicorn gthread 下调用 | `preexec_fn` 只在 fork 后、exec 前执行，官方文档标注「多线程不安全」；改用 `subprocess.run(..., preexec_fn=)` 的同时**保持函数体极简**（只调 setrlimit），不使用锁/内存分配 |

## 最重要的两条

**R-04（读文件）**：本 CR **不能彻底防住**。要彻底防需要 mount namespace / seccomp / 独立沙箱服务，当前 Docker-in-Docker 架构做不到。
实际缓解靠：L1 进程隔离（崩溃不影响主服务）+ L3 环境变量清空（拿不到 DB 串）+ L4 拦 `open`（常见路径）。

**判断标准**：本 CR 把「**一行 exec 就能 RCE 并能读光所有密钥**」降到「**需要绕过 AST + 仍可能读到文件，但拿不到环境变量、且搞不垮服务**」。
这已是当前架构下的合理上限；要进一步加固，应单独立项做「独立沙箱服务」。
