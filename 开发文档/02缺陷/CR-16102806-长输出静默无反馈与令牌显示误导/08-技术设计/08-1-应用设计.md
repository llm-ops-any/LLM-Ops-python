## 二、FIX-1 前端静默计时

### 2.1 为什么不用 ping 事件驱动

心跳 `ping` 是**后端每 10 秒发一次**，间隔太粗（精度 10 秒），且三处视图都要改事件分支。改用**前端本地计时器**：

- 请求开始 → 启动 1 秒粒度的计时器
- 每收到任意**非 ping**事件 → 计时归零
- 请求结束（成功/失败/停止）→ 停止计时

优点：精度 1 秒、不依赖后端心跳、后端若去掉 ping 也不影响。

### 2.2 组合式函数签名

```ts
// ui/src/hooks/use-stream-idle.ts
export const useStreamIdle = (threshold: number = 20) => {
  const idleSeconds = ref(0)                                  // 距上次内容块的秒数
  const isIdle = computed(() => idleSeconds.value >= threshold) // 是否已达到提示阈值

  const startIdleWatch = () => { /* 归零 + setInterval(1s) */ }
  const touchActivity = () => { idleSeconds.value = 0 }        // 收到内容事件时调用
  const stopIdleWatch = () => { /* clearInterval + 归零 */ }

  return { idleSeconds, isIdle, startIdleWatch, touchActivity, stopIdleWatch }
}
```

- 阈值 **20 秒**：正常短问答（<10 秒）完全不打扰；实测的 105 秒静默会在第 20 秒给出提示。
- **必须 `onBeforeUnmount` 里 `stopIdleWatch`**，否则路由切走后计时器泄漏。

### 2.3 界面呈现

在现有「停止响应」按钮**同一行左侧**加一段提示，不改按钮位置：

```vue
<div v-if="task_id && chatLoading" class="flex items-center justify-center gap-3">
  <span v-if="isIdle" class="text-xs text-gray-500">
    模型正在生成，已静默 {{ idleSeconds }} 秒…
  </span>
  <a-button ...>停止响应</a-button>
</div>
```

- `isIdle` 为 false 时不渲染任何文字 → 常规问答零视觉变化（AC-02）。
- 文案用「静默」，不用「卡住」，避免在最终成功时显得像出错。

## 四、FIX-3 后端静默超时

### 4.1 现状

`agent_queue_manager.listen()` 只有一个 `listen_timeout = 600`（总时长），静默期不区分。

### 4.2 改动

```python
listen_timeout = 600
silent_timeout = current_app.config.get("AGENT_SILENT_TIMEOUT", 300)   # 新增
last_activity_time = time.time()                                       # 新增

while True:
    try:
        item = self.queue(task_id).get(timeout=1)
        if item is not None and getattr(item, "event", None) != QueueEvent.PING:
            last_activity_time = time.time()        # 只有内容事件才算"活着"
        ...
    except queue.Empty:
        continue
    finally:
        # 现有 ping / listen_timeout / stop 逻辑保持不变
        # 新增：静默超时判定（先于总超时判定）
        if time.time() - last_activity_time >= silent_timeout:
            self.publish(task_id, AgentThought(
                id=uuid.uuid4(), task_id=task_id,
                event=QueueEvent.ERROR,
                observation=f"模型已静默 {silent_timeout} 秒未返回内容，判定上游中断，请重试",
            ))
```

判定顺序：**静默超时 → 总超时 → 停止**，静默超时命中后 `publish` 会自动 `stop_listen`。

### 4.3 阈值取值依据

| 实测静默 | 是否应放过 |
|---|---|
| 0 秒（短问答） | ✅ |
| 105 秒（本次事故，最终成功） | ✅ **必须放过** |
| 300 秒 | 阈值 |

取 **300 秒**：是实测最长正常静默的 2.9 倍，仍有 2 倍安全余量，又把最坏等待从 600 秒砍半。

### 4.4 配置化

`docker/docker-compose.yaml` 的 `x-llmops-common-env` 增加：

```yaml
AGENT_SILENT_TIMEOUT: 300
```

`app.py` 的 `Config` 读取该环境变量（缺省 300），便于压测时临时调小验证 AC-04。

## 五、事件契约影响

**零变更**。SSE 事件类型仍为 `agent_message / agent_thought / agent_action / agent_end / error / timeout / ping`，前端解析逻辑不动，只是**新增对 ping 之外的静默感知**（纯本地计时）。`CR-16102803` 的语音接口不受影响。

## 六、不做与理由

| 项 | 理由 |
|---|---|
| 后端 ping 携带「距上次内容秒数」 | 需要改事件结构 + 前端解析，收益仅是省一个本地计时器，不值 |
| 流式实时估算 Token | 估算值必然与最终值不一致，产生「跳变」，比 `0` 更让人困惑 |
| 降低 `listen_timeout` | 长任务（如 20 页 PPT 文案）可能合法超过 300 秒，用静默维度替代 |
