# CR-16102804 决策记录

## D-01 用 CosService 的私有方法，不改共享服务

- **背景**：原项目工具里调 `cos_service.get_client()` / `cos_service.get_bucket()`，而本项目的 `CosService` 把它们收敛成了 `_get_client()` / `_get_bucket()`（公开的是 `upload_file(FileStorage, ...)` / `get_file_url(key)`）。
- **决策**：在工具里调私有方法，并在注释里写明差异。
- **被否**：① 给 `CosService` 加一个 `upload_local_file(path, key)` 公开方法 —— 为一个工具改共享服务，影响面更大，且 `upload_file` 的签名是给"用户上传"用的（需要 `Account`、`FileStorage`），语义不匹配；② 绕开 CosService 自己 new 一个 client —— 会重复配 `CosSecretId` 等，且拿不到 `get_file_url` 的域名兜底。
- **代价**：工具与 `CosService` 内部结构耦合。若将来改私有方法名，这里会断——已加注释提示。
- **决策人**：DEV。

## D-02 依赖同时改 `requirements.in` 与 `requirements.txt`

- **背景**：`开发规范.md` §一 明确「`requirements.txt` 是 pip-compile 生成物，手改会被下次编译覆盖；要加依赖改 `requirements.in` 后重编」。
- **决策**：两处都改。`.in` 声明 `mistune` + `python-pptx`；`.txt` 手工补 4 个包（`mistune` / `python-pptx` / `pillow` / `xlsxwriter`），版本照课程原项目锁定（`3.1.2` / `1.0.2` / `11.1.0` / `3.2.2`），并按 pip-compile 的格式补 `# via` 注释与字母序位置。
- **理由**：本机没有可靠网络跑 `pip-compile`，但版本必须与原项目一致才能对照课程；写成编译产物格式，下次真跑 `pip-compile` 时输出应基本一致。
- **代价**：手工插入可能与真实编译结果有细微差异（例如 `pillow` 的 via 列表在真实编译里还会列出 `-r requirements.in` 之外的来源）。下次重编时以编译结果为准。
- **决策人**：DEV。

## D-03 顺手修正原项目的一处日志 bug

- **原代码**：`logging.error("markdown_to_pptx出错: {error}s", {"error": error}, exc_info=True)` —— 用 `{}` 占位 + 传 dict + 尾部多一个 `s`，日志实际打成字面量，出错时看不到原因。
- **决策**：改成标准的 `logging.error("markdown_to_pptx出错: %s", error, exc_info=True)`。
- **理由**：这个工具的失败路径（COS 未配置、markdown 里有非法图片）恰恰最需要日志；不改等于把唯一的排查线索丢掉。
- **影响**：仅日志文本，返回值不变。
- **决策人**：DEV。

## D-05 品牌文案「慕课」→「成长」（与"照原样移植"冲突，按品牌口径优先）

- **发现**：按原项目原样移植后，生成的 PPT 首页副标题是「由**慕课**LLMOps平台生成」（下载文件解析确认）。
- **决策**：改为「由成长LLMOps平台生成」。
- **理由**：共享库品牌口径明确「全仓『慕课』→『成长』、imooc 全清，零残留」；这是**对外可见**的产物（用户下载的 pptx 里会带），比"移植保真"优先级更高。
- **被否**：保留原文案 —— 会让品牌残留通过用户下载的文件流出去，属于口径倒退。
- **代价**：与原项目生成结果有 1 处文本差异，对照课程时会看到。
- **决策人**：DEV（依据既有口径），已写入验收报告请 PO 过目。
