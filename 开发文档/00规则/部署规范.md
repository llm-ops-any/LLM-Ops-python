# 部署规范

> **本文件管「怎么部署」**：起服务、改完什么动作才生效、部署后怎么验、出问题怎么退。
> 不写「配什么值」——那在根目录 `环境变量配置说明.md`；不写「为什么这么定」——那在各 CR 的 `决策记录.md`。
> 本文只记**稳定规则**：不写部署进度（哪台机、谁部署、最近一次时间），不出现任何密钥 / 密码 / 账号值。
> 归属：`00规则/`，与具体 CR 无关；改动本文件需开 CR。

## 一、部署形态

编排文件 `docker/docker-compose.yaml`，全部服务在同一 Docker 网络内，**对外只有 nginx 的 80 端口**。

| 容器 | 镜像 | 宿主端口 | 职责 |
|---|---|---|---|
| `llmops-nginx` | `nginx:latest` | **80**（唯一对外） | 反代：`/api/` → api:5001（去掉 `/api` 前缀），其余 → ui:3000 |
| `llmops-ui` | `llmops-ui:0.1.0` | `127.0.0.1:3000` | 前端静态站（Vite 构建产物 + 内置 nginx） |
| `llmops-api` | `llmops-api:0.1.0` | `127.0.0.1:5001` | Flask + gunicorn（4 worker × 4 线程），启动时负责 alembic 迁移 |
| `llmops-celery` | **同 api 镜像** | 无 | Celery worker（4 并发），异步任务 |
| `llmops-db` | `postgres:15-alpine` | `127.0.0.1:5432` | 业务库 `llmops` |
| `llmops-redis` | `redis:6-alpine` | `127.0.0.1:6379` | 缓存 / Celery broker（`db=1`） |
| `llmops-weaviate` | `semitechnologies/weaviate:1.28.4` | `127.0.0.1:8080`、`50051` | 向量库（鉴权开启，向量化模块 `none`，向量由应用侧算） |

- api 与 celery **同一个镜像**，靠 `MODE`（`api` / `celery`）在 `api/docker/entrypoint.sh` 分流；
  迁移只由 api 跑（`MIGRATION_ENABLED=true`，celery 为 `false`），避免重复执行。
- 数据全部落在 `docker/volumes/`：`db/data`、`redis/data`、`weaviate/`、`app/storage`。
- 当前为 **IP + HTTP 直服**：`docker/nginx/ssl/` 已挂载但 443 未开；启用 HTTPS 需同时改
  `docker-compose.yaml` 的端口映射与 `docker/nginx/conf.d/default.conf` 的 server 块，属独立变更。

## 二、前置条件

1. Docker Desktop（含 `docker compose` v2）可用，能 `docker compose version`。
2. **`docker/.env` 存在且填全**：由模板 `docker/.env.example` 复制为 `docker/.env` 后逐项填，
   取值范围见根目录 `环境变量配置说明.md`。该文件已被 gitignore，**不进仓库**。
3. 密码类取值只能用字母数字：含 `@` `:` `/` 会破坏数据库连接串。
4. 工作目录一律是 **`docker/`**（compose 文件与 `.env` 同目录），不在仓库根执行。

## 三、首次部署

```powershell
# 从仓库根进编排目录（本文所有 compose 命令都在 docker/ 下执行）
cd docker

# 1) 构建并启动（首次必须 --build：llmops-api:0.1.0 / llmops-ui:0.1.0 本地不存在）
docker compose up -d --build

# 2) 看状态与 api 启动日志
docker compose ps
docker logs llmops-api --tail 60
```

启动顺序与预期耗时：

1. `llmops-db` 空数据卷时会执行 `docker/postgres/init.sql`（**只有空卷才触发，已有数据不再执行**）；
2. `llmops-api` 先跑 `flask db upgrade` 迁移，再起 gunicorn；
3. api 首次要加载 jieba / FAISS，**gunicorn 约 20~30 秒才 listen**，这段时间访问报 502 属正常，重试即可。

平台**没有注册接口**（账号只在 GitHub OAuth 授权时自动创建）。未配 OAuth 的环境必须手工建管理员：

```powershell
docker compose cp create_admin.py llmops-api:/tmp/create_admin.py
docker compose exec llmops-api python /tmp/create_admin.py <email> <password>
```

- 密码规则：8–16 位，至少一个字母 + 一个数字。
- 邮箱**不能用 `.local` / `.test` 等保留域名**，会被邮箱校验直接拦掉，报「登录邮箱格式错误」。

访问入口：**`http://localhost`**。

## 四、改了什么 → 执行什么（最容易错的一张表）

| 改了什么 | 执行 | 为什么 |
|---|---|---|
| 后端 `api/**/*.py`、模型 YAML `api/internal/core/language_model/providers/**/*.yaml` | `docker compose build llmops-api` → `docker compose up -d llmops-api llmops-celery` → `docker compose restart llmops-nginx` | 代码与 YAML **烘进镜像**，改文件不热更新；celery 同镜像，必须一起换 |
| 前端 `ui/src/**` | `docker compose build llmops-ui` → `docker compose up -d llmops-ui` → `docker compose restart llmops-nginx` | `dist/` 是构建产物，打进镜像 |
| `docker/.env` | `docker compose up -d` → `docker compose restart llmops-nginx` | env 是**运行时注入**，`up -d` 才会用新值重建容器 |
| `docker/docker-compose.yaml` | `docker compose up -d` | 编排变更靠 recreate 生效 |
| `docker/nginx/**`（`nginx.conf` / `proxy.conf` / `conf.d/`） | `docker compose restart llmops-nginx` | nginx 配置是挂载卷，重启即读新文件 |
| 页面「设置 → 大模型设置」保存的模型配置 | **无需任何命令** | 存库、≤10 秒生效；`.env` 里的 `OPENAI_*` 降级为兜底 |
| 新增环境变量 | 先在 `docker-compose.yaml` 的 `x-llmops-common-env` 锚点加一行，再按 env 那行走 | 锚点逐个按名引用，不登记则容器里 `os.getenv` 拿到 `None` 且**不报错** |

**下面三条是硬约束，违反时大多不报错：**

1. **`docker compose restart` 不重读 env**：只重启进程，容器沿用创建时的 `environment`。
   改完 env 只 `restart`，新值不生效、状态仍是 `Up`。核对：`docker exec llmops-api printenv` 与 `docker/.env` 逐项比。
2. **重建 / 重启 api 后必须 `restart llmops-nginx`**，否则**全站 502**：nginx 的 `proxy_pass` 写服务名，
   上游 IP 在启动时解析并缓存。**判别：经 80 端口 502、直连 `127.0.0.1:5001` 正常 ⇒ 就是这个，不用翻 api 日志。**
3. **代码与模型 YAML 不是挂载的**：改完不 `build`，等于没改；日志里也看不到任何「配置未生效」提示。

## 五、部署后验收

最小 4 条（完整 8 条判据见 `团队配置.md`「后端端到端清单」，**以那份为准，此处不复制**）：

```powershell
# 1) 服务存活（PowerShell 里 curl 是 Invoke-WebRequest 别名，带 -s 等参数请用 curl.exe）
curl.exe -s http://localhost/api/ping
# 2) 页面可达
curl.exe -s -o NUL -w "%{http_code}" http://localhost/home
# 3) 无异常日志（ResourceWarning 等无害告警除外）
docker logs llmops-api --tail 100
# 4) 向量化 / 模型链路（需登录态 token，从环境变量传，不写进文件）
docker logs llmops-celery --tail 60
```

任一条 5xx 或 `code≠success` 即判部署失败，**不允许用「其余都过」折算**；失败要贴响应体与 `docker logs` 片段。

## 六、回滚与数据保护

```powershell
# compose 命令在 docker/ 下执行，git 命令在仓库根执行（下同）
# 停止服务，保留数据（volumes/ 目录不动）
docker compose down

# 代码回滚：镜像 tag 固定为 0.1.0，没有历史镜像可退 ⇒ 回滚靠源码
git checkout <上一个可用提交>          # 仓库根
cd docker                              # 回到编排目录
docker compose up -d --build
docker compose restart llmops-nginx

# 备份 / 恢复业务库：先写到容器内再拷出，别用 PowerShell 的 `>`（默认 UTF-16 编码）
docker exec llmops-db pg_dump -U postgres -d llmops --no-owner --no-privileges --encoding=UTF8 -f /tmp/backup.sql
docker cp llmops-db:/tmp/backup.sql backup.sql
docker exec llmops-db rm -f /tmp/backup.sql

# 恢复（目标是已有库，会与现有数据冲突，慎用）
Get-Content backup.sql | docker exec -i llmops-db psql -U postgres -d llmops
```

数据相关的三个高危动作，动手前先确认有备份：

1. **删 `docker/volumes/` 下任目录 = 删数据**（db / redis / weaviate / app storage）。删 db 后重启会重新执行 `init.sql`，
   库是空的，业务数据无法恢复。
2. **改 `POSTGRES_PASSWORD` 不会改已有数据卷里的密码** ⇒ 必须清 `volumes/db/data` 重建（**丢数据**）。
3. **改 `JWT_SECRET_KEY` 会让所有已登录用户立即掉线**，需重新登录（不丢数据）。

### 把现有数据带到新环境

`docker/postgres/` 挂进容器的 `/docker-entrypoint-initdb.d`，**空数据卷**首次启动按文件名字典序执行。
因此把本机库 dump 成 `docker/postgres/llmops_data.sql`（`i` < `l`，排在 `init.sql` 之后 ⇒ 扩展先建、表后建），
新环境起来就自带数据：

```powershell
# 在 docker/ 下执行
docker exec llmops-db pg_dump -U postgres -d llmops --no-owner --no-privileges --encoding=UTF8 -f /tmp/llmops_data.sql
docker cp llmops-db:/tmp/llmops_data.sql postgres/llmops_data.sql
docker exec llmops-db rm -f /tmp/llmops_data.sql
```

四条边界：

- 快照含**真实账号邮箱、密码 hash、`api_key` 密文** ⇒ 已在 `.gitignore` 排除，**不进版本库**，只在本机留档。
- **只在空数据卷生效**；已有数据的库不会自动导入（防覆盖）。
- **不含 Redis / Weaviate**：`dataset` / `document` 的向量要重新向量化，否则检索为空。
- 快照带 `\restrict`（PG 15.19 起的安全令牌），用明显更老的 `psql` 恢复会报语法错——恢复用同版本或更新的客户端。

## 七、子项目

| 目录 | 形态 | 部署方式（相对仓库根的目录） | 入口 |
|---|---|---|---|
| `ui-to-code/` | 独立 compose（**不在主 compose 内**） | `cd ui-to-code` → `docker compose up -d --build` | `http://localhost:3001`（冲突时改 `APP_PORT`） |
| `echoMimic/` | 本地 Python 环境，**非容器** | `cd echoMimic` → 装依赖 + 放权重后按该项目自身说明起；权重缺失时跑不起来 | 见 `00规则/项目概述.md` 第 10 节 |
| `gradio-demo/` | 本地 `.venv` + Gradio | `cd gradio-demo` → `python webui.py` | `http://127.0.0.1:7860` |

`ui-to-code/` 三处与主平台不同，改它时别照抄主平台命令：

- 凭证走 `env_file: .env` 运行时注入，**不进镜像**；
- 容器内访问平台必须用 `http://host.docker.internal/api/openapi`（容器里的 `localhost` 是容器自己）；
- 基础镜像是 `node:22-slim`，**不要换回 alpine**：`package-lock.json` 缺 `@tailwindcss/oxide-linux-x64-musl` 节点，alpine 构建必失败。

## 八、硬禁区

1. **`docker/.env` 不进仓库**（已 gitignore），不贴进 `开发文档/`、审计、聊天记录。
2. **不用 `docker compose restart` 代替 `up -d`** 来应用 env / 编排变更。
3. **不跳过 `restart llmops-nginx`** ——省这一步省不出时间，只会得到全站 502。
4. **不手工改业务表数据**（除 `create_admin.py` 建账号）；改数据走迁移或页面。
5. **不把 `ui/dist/`、`docker/volumes/` 纳入版本控制**（构建产物 / 容器数据）。
6. **不在 `docker/` 之外执行 compose 命令** ——找不到 `.env`，起来的是「变量全空」的一套容器。

## 九、坑速查

| 现象 | 大概率原因 | 动作 |
|---|---|---|
| 全站 502，直连 `127.0.0.1:5001` 正常 | nginx 缓存了旧上游 IP | `docker compose restart llmops-nginx` |
| 全站 502，刚起不久 | api 还在迁移 / 加载 jieba、FAISS | 等 20~30 秒重试 |
| 改了 `.env` 但容器里还是旧值 | 只做了 `restart` | `docker compose up -d` + 核对 `printenv` |
| 改了后端代码但行为没变 | 没 `build` | `docker compose build llmops-api` 后 `up -d llmops-api llmops-celery` |
| 容器里 `os.getenv` 拿到 `None` | 新变量没进 `x-llmops-common-env` 锚点 | 锚点加一行后 `up -d` |
| `docker exec` 跑脚本报 `No module named 'internal'` | `python /tmp/x.py` 的 `sys.path[0]` 是 `/tmp` | 加 `-e PYTHONPATH=/app/api` |
| 上传图片 / 图标 403 全裂 | COS 桶权限不是「公有读」 | 改桶权限（代码只拼 URL、不签名） |
| 某应用每句话都 500 | 该应用挂了缺 Key 的内置工具（构造即校验） | 看 `docker logs llmops-api --tail 120`，补 Key 或去掉该工具 |
