# CR-16102806 问题（现象 · 证据 · 根因）

> 缺陷不停 G1。本文件是本次修复的**唯一事实来源**，所有结论都可在下方「证据」段复算。

## 一、现象

**PO 原话（2026-10-28 18:17，附截图）**：

> PPT文案生成助手，使用了ppt插件，没有完全输出完，一直加载中，但是我看应该是加载完了

截图内容：

```text
以上是完整的PPT内容框架。请确认是否需要调整，确认后我将为你生成PPT文件。
✓ 7.13s | 0 Tokens
                    [ 停止响应 ]
```

三点可观察异常：

| # | 现象 | 用户预期 |
|---|---|---|
| S-1 | 文本已输出到语义完整的收尾句，界面仍在转圈、"停止响应"不消失 | 应该结束 |
| S-2 | 计时停在 **7.13s** 不再增长 | 计时应反映真实耗时 |
| S-3 | Token 显示 **0** | 应显示实际消耗 |

## 二、证据

### 2.1 库内原始数据（`message` 表）

```sql

from message where app_id='3e9d86fd-a565-4578-a364-3d2706e2da86'

```

| id | query | answer 长度 | tokens | latency | status | created_at |
|---|---|---|---|---|---|---|
| `c643beee-7c56-46fa-beed-36ca78aa6db6` | 程序员年终汇报ppt | **2210 字** | **2839** | **112.14 s** | normal | 10:15:51 UTC（18:15:51 CST） |
| `de9e27ca-024c-4d1a-94a8-14729543c42d` | 程序员年终汇报ppt | 2221 字 | 4677 | 4.11 s | normal | 18:19:34（复测，命中上下文） |

### 2.2 时间线对齐（决定性证据）

| 时刻 | 事件 |
|---|---|
| 18:15:51 | 请求发起 |
| **18:17:32** | **PO 截图时刻 = 第 101 秒**（截图 `7.13s` 是最后一次吐字的耗时快照） |
| 18:17:43 | 请求真正结束，`latency = 112.14s` |

⇒ **不是「输出完了不收尾」，是「确实还没跑完」**：前 7.13 秒吐出阶段性收尾句，随后**静默约 105 秒**无任何内容块，最后才补完剩余正文（结尾为「总结与展望」，共 2210 字）。

### 2.3 为什么 105 秒静默期间连接没断、也没报错

三层超时全部对齐在 **600 秒**，任一层都不会提前打断：

| 层 | 配置 | 位置 |
|---|---|---|
| openai SDK | 默认 `timeout=600s` | `langchain_openai.ChatOpenAI` 未显式设置 |
| 队列监听 | `listen_timeout = 600` | `internal/core/agent/agents/agent_queue_manager.py:46` |
| nginx | `proxy_read_timeout 600s` / `proxy_send_timeout 600s` | `docker/nginx/proxy.conf` |

同时心跳**每 10 秒发一次**（`agent_queue_manager.py:64-71`），连接保持活跃，因此不会触发任何超时或断连。

### 2.4 为什么前端毫无反馈

心跳事件发出来了，但前端**主动丢弃**：

```ts
// ui/src/views/pages/HomeView.vue:115
if (event !== QueueEvent.ping) {
  ...  // ping 被整段跳过，UI 不做任何事
}
```

`PreviewDebugChat.vue`、`web-apps/IndexView.vue` 同构。⇒ **心跳救了连接，但没救用户**。

### 2.5 为什么 Token 恒为 0

`token` 只在**整段输出结束后**统一计算，且只在最后一条事件里下发一次：

```python
# internal/core/agent/agents/function_call_agent.py:205-220
input_token_count  = self.llm.get_num_tokens_from_messages(state["messages"])
output_token_count = self.llm.get_num_tokens_from_messages([gathered])
...
total_token_count = input_token_count + output_token_count
```

流式过程中所有 `agent_message` 事件的 `total_token_count` 均为默认值 `0`（`queue_entity.py:57`）。

⇒ **`0 Tokens` 是「还没结束」的副作用显示**，不是统计坏了。但显示成 `0` 会让人误判成「统计失败」或「已经跑完」。

### 2.6 复现与对照

| 测试 | 命令 | 结果 |
|---|---|---|
| 短问题（无工具） | `用一句话说明什么是LLMOps` | 1.34s 正常 `agent_end`，无静默 |
| 长输出（命中上下文） | `程序员年终汇报ppt`（第二次） | 4.11s 正常 `agent_end` |
| 长输出（首次，冷上下文） | `程序员年终汇报ppt`（18:15:51） | **112.14s，其中静默 105s** |
| nginx 链路收尾 | `curl -N` 观察 | `agent_end` 后连接正常关闭，退出码 0 |

⇒ **后端链路本身没有 bug**：流能正常收尾。问题在**上游静默期的可观测性**与**前端反馈缺失**。

## 三、根因

| # | 根因 | 归属 | 能否修 |
|---|---|---|---|
| **R-1** | 上游模型/网关在长输出中途断流约 105 秒（`deepseek-v4-flash` 经 uino 中转），代码侧对该静默**无感知、无判定** | 上游行为 + 我方缺保护 | 不能让它变快，但**能感知并提示** |
| **R-2** | 心跳（`ping`）每 10 秒正常发出，但**三处聊天界面全部丢弃**，静默期 UI 零变化 | 我方前端 | ✅ 可修 |
| **R-3** | `total_token_count` 仅在结束时下发的设计，使流式期恒显示 `0 Tokens`，与「未完成」语义冲突 | 我方前端展示 | ✅ 可修 |
| **R-4** | 三层超时对齐 600 秒且互相兜底失效，最坏情况干等 10 分钟才收到 `timeout` 事件 | 我方配置 | ✅ 可收紧 |

## 四、非缺陷项（一并记录，避免误判）

1. **该应用 `tools = []`，一个工具都没挂**：
   ```sql
   select tools from app_config where id='eca3e7cf-dfb2-4fbb-b040-877a6f20285c';
   -- []
   ```
   模型说的「确认后我将为你生成PPT文件」是**无工具可用时的口头承诺**，不会产出 `.pptx`。
   此项**不是缺陷**（pptx provider 已由 `CR-16102804` 注册成功），属于应用配置遗漏；PO 已于 18:43 反馈「ppt 验证了没问题」，即已自行挂载并验证。

2. **`latency` 停在 7.13s 不是计时器坏了**：`latency` 是「最后一次收到内容块」的耗时，静默期没有新内容块，自然不增长。这是 R-1 的表象，不是独立缺陷。
