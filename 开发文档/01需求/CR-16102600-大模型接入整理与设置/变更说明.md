# 变更说明 · CR-16102600

> 记录「设计基线 → 实际实现」的差异。设计文档（`设计/应用设计.md`）仍是基线，**以本文件的差异为准**。

## 差异 1（重要）：向量化模型由 `qwen3-embedding-8b` 改为 `text-embedding-v4` + `dimensions=1536`

**触发**：施工期做 FR-10（对话与向量化共用配置）的真实调用验证时，`embed_query` 返回

```
openai.InternalServerError: Error code: 503 - {'error': {'message': '分组 default 下模型 qwen3-embedding-8b 无可用渠道（distributor）'}}
```

**排查结论**：

1. 线上 `/v1/models` 里确实列出了 `qwen3-embedding-8b`，但**没有任何可用渠道**，属「列表里有、调不通」；
2. 原始默认值 `text-embedding-3-small` 同样 503 —— 也就是说**本次改动之前，知识库向量化链路本来就是断的**，与本次改造无关；
3. `.env` 里原先的注释「阿里 text-embedding 系列与 langchain 参数格式不兼容（报 400）」是**误判**：真实原因是 langchain 的 `OpenAIEmbeddings` 默认 `check_embedding_ctx_length=True`，会先用 tiktoken 把文本切成 token 整数数组再发送，中转平台直接 400（`contents is neither str nor list of str`）；
4. 加 `check_embedding_ctx_length=False` 后，`text-embedding-v3/v4/v1` 全部 200。

**模型选择实测**（`POST /v1/embeddings`）：

| 模型 | 无 dimensions | dimensions=1536 | 采用 |
|---|---|---|---|
| `qwen3-embedding-8b` | 503 | 503 | ✗ |
| `text-embedding-3-small` | 503 | - | ✗ |
| `text-embedding-v4` | 200 / 1024 | 200 / 1536 | **✓** |
| `text-embedding-v3` | 200 / 1024 | 400 维度非法 | ✗ |
| `text-embedding-v1` | 200 / 1536 | 200 / 1536 | 备选 |

**同向量空间验证**（关键依据，避免选了能跑但检索无效的模型）：用同一个 query 在预置 FAISS 索引（`/app/api/internal/core/vector_store`，`ntotal=260`、`d=1536`）上做 `similarity_search_with_score`：

| 模型 | Top-1 L2 距离 | 命中内容 |
|---|---|---|
| `text-embedding-v4`（dims=1536） | **1.8814** | 接口文档 JSON 片段（相关） |
| `text-embedding-v1` | 10215.16 | 无关片段（等于随机） |

⇒ 预置索引与 `text-embedding-v4` 同一向量空间，辅助 Agent 的扩展知识库可用。

**改动点**：

| 文件 | 改了什么 |
|---|---|
| `api/internal/service/embeddings_service.py` | `DEFAULT_EMBEDDINGS_MODEL = "text-embedding-v4"`；`check_embedding_ctx_length=False`；缓存命名空间改为 `embeddings:<model>:<dims>` |
| `docker/.env` | `EMBEDDINGS_MODEL=text-embedding-v4`，并把「阿里模型与 langchain 不兼容」的错误注释改成真实原因 |
| `api/internal/service/faiss_service.py` | 转工具前 `self.faiss._embeddings = self.embeddings_service.embeddings`（**必须写底层字段**：`FAISS.embeddings` 是只读 property，直接赋值会 `AttributeError`，见 `审计-2.md` 21:17 那条），否则知识库检索仍用启动时的旧凭证 |

**为什么不算突破 D10**：D10 约束的是「不改维度」（1536）与「不做页面可配」，两者都没破；这里改的是**默认模型名**，且是因为原模型根本调不通。维度、FAISS 索引、页面字段全部未变。

**需 PO 追认**：D11 已记入 `决策记录.md`，请在验收时确认。不追认的替代方案是回退到 `qwen3-embedding-8b`，代价是知识库向量化重新变成 503 不可用。

## 差异 2：加密模块位置

设计写 `api/pkg/secret.py`，实际放在 **`api/internal/lib/secret.py`**。理由：`pkg/` 在本项目里是「与业务无关的通用脚手架」（分页、SQLAlchemy 封装、JWT 等），而密钥派生依赖 `JWT_SECRET_KEY` 这一业务配置；放 `internal/lib/` 与 `internal/lib/helper.py`、`internal/lib/id_generator.py` 一致，且 `pkg/` 已被 `internal` 大量引用，反向放会加重层次混乱。

## 差异 3：接口响应字段名

设计写 `provider_label`，实际为 **`source_label`**。理由：该字段描述的是「配置来源」而非「供应商」，叫 `provider_label` 会与已有的 `/model-providers`（供应商列表）语义混淆。

## 差异 4：字段长度上限

设计未写上限，实现取 `Length(max=512)`（`base_url` 与 `api_key` 同）。理由：实际中转地址 < 100 字符、密钥 51 字符，512 足够且能挡住误粘贴的长文本。

## 差异 5：`Chat` 的 token 计算

`providers/uino/chat.py` 里 `get_num_tokens_from_messages` 直接复用父类实现（删除重复逻辑）。设计未提及，属实现细节。
