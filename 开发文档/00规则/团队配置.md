> **一个人有多个 git email**（工作邮箱 + 个人邮箱 + 另一台机器）：**加多行，人编号填同一个**。
> 取号靠 email 查表，一个 email 查不到就会问你 —— 别让它猜。
>
> **两个人共用同一个 git 账号**（外包 / 临时同事）：这是唯一会让「人编号」失效的情况，
> 因为查表只能查到同一个 email。处理方式二选一：
> ① 给各自配独立 email（推荐）；② 启动前设环境变量 `AIDLC_PERSON=2`，技能优先读它。
> 共用账号还不设变量 ⇒ 两人会拿到同一个人编号，**审计记录将无法区分是谁做的**。
>
> **人编号**是 CR 号的第一位（`P`），1~9，**一人一个、分配后永不改**。
> CR 号 = `P` + 年末位 + 月日 + 当日序号，例 `16102100` = 人1 / 2026 / 10-21 / 当天第 00 个。
> 首位是人 ⇒ **两个人永远不共享号段**，从结构上不可能撞号。换人编号会让历史 CR 对不上人。
> 单人项目只需给自己一个 `1`。

> 2 人团队允许一人兼两角，但 `DEV` 不能给自己批代码（见 role-gates「四眼原则」）。
> **本项目是单人（一人兼三角），G3 不存在外部批准人**：代码合入不停门禁，但必须在 `审计-1.md` 写明「单人自审」。

## 测试策略（三选一 + 本项目专用档）

**本项目取 `后端端到端`**：开发完 → **静态检查 + 后端端到端清单（真打接口，经 nginx）** → 清单全绿才算完成。

| 档位 | 做什么 | 什么时候必须升档 |
|---|---|---|
| `全量` | 新增用例 + 全量回归 + 人工走查 | 有持久化数据、有数据迁移、会多轮迭代 |
| `仅回归` | 只跑既有用例，不新增 | 改动碰了数据模型或渲染结构，但已有用例覆盖 |
| `仅静态` | 语法检查 + 静态扫描 + 人工自测 | — |
| `后端端到端`（本项目） | 静态检查 + 下表 8 条真打清单，逐条贴状态码与响应片段 | 清单无法覆盖的并发/迁移/前端渲染问题 ⇒ 临时补一次 pytest 或 vitest |

### 后端端到端清单（每轮交付逐条执行，全绿才算完成）

| # | 验证项 | 命令（宿主机，经 nginx） | 通过判据 |
|---|---|---|---|
| 1 | 服务存活 | `GET /api/ping` | 200 且 `code=success` |
| 2 | 登录态可用 | `GET /api/account` + `Authorization` | 200 且返回当前用户 |
| 3 | 新接口通 | `GET /api/model-provider` | 200 且 `masked_api_key=****`，响应全文不含 `sk-` |
| 4 | 外部链路通 | `POST /api/model-provider/test-connection` | 200 且 `ok=true`、`model_count>0` |
| 5 | 保存即生效 | `POST /api/model-provider` → 再 `GET` | 200；`source=database`；**10 秒内**读到新值 |
| 6 | 全链路（鉴权→业务→DB→向量→模型） | `POST /api/assistant-agent/chat`（SSE） | 200 且有内容增量，`total_token_count>0` |
| 7 | 页面可达 | `GET /home` | 200 |
| 8 | 无异常日志 | `docker logs llmops-api --tail 100` | 无 `Traceback` / `ERROR`（`ResourceWarning` 等无害告警除外） |

> **当前档位是 `后端端到端`，因此**：
> - 每轮交付**必须逐条打**上面 8 条，把真实状态码与关键响应片段贴进 `测试记录.md`；没打就是没做；
> - **前端 vitest、pytest 单元/接口用例不纳入必跑项**，资产保留不动：`api/test/` 现有 59 条（本次 CR 新增）+ 既有用例、`ui/src/views/openapi/playground/__tests__/`；
> - 清单里任何一条 5xx 或 `code≠success`，一律算失败，不允许用「其余都过」折算；失败必须贴响应体与 `docker logs` 片段；
> - **重建 api 容器后先 `docker restart llmops-nginx` 再执行清单**，否则第 1–7 条会全 502（2026-10-26 已踩）；
> - **降档留痕**：这是从 `全量` 降档，`验收报告.md` 必须写明「本轮未跑自动化用例」及未覆盖风险；
> - **标签必须与实际动作一致**：只打了清单就标 `后端端到端`；若某轮顺手跑了 pytest，在记录里单列结果，不要把档位改回 `全量`；
> - **需要时的一条命令**（不改档位，只补测）：`docker exec -e PYTHONPATH=/app/api -w /app/api llmops-api python -m pytest test/internal/lib test/internal/service -q`（46 条，不依赖库与登录态）。

## 审批模式（五选一）

> 这张表是**五档的完整含义**，与上方「审批模式」那一行配套使用，**两处都不许删**。
> 只写当前档、把其余四档删掉，等于让后来的人以为没有别的选择。

| 模式 | 行为 | 适用 |
|---|---|---|
| `全自动` | **不设门禁**，澄清问题自答，按推荐项跑完整流程，收尾交 `验收报告.md`；只在四种情况下刹车 | 小工具、原型、试验性代码 |
| `仅需求审批` | **只留 G1**：需求可问一轮（≤5 题），`需求.md` 出来后停下等批准；批准后 G2/G3 不生效，按全自动规则跑完 | 需求要人把关、实现可托付（单人推荐） |
| `关键三关` | 只在 G1 需求 / G2 设计 / G3 代码合入三处停 | 默认，2–3 人团队 |
| `每阶段` | 每个阶段结束都停 | 对外交付、高风险 |
| `只在交付验收` | 中间不停，最后验收一次 | 极小改动 |

**全自动模式的四条刹车**：需求自相矛盾 / 要执行不可逆或对外动作 / 与需求文档明确冲突 / 必须加需求外功能。
遇到只问一个问题，答完继续自动跑。

**全自动不等于免审计**：每次自动决策照样写进 `审计.md`（`Decision` + `Basis` + `Auto`），
跑完必须产 `开发文档/<类型目录>/CR-0X-<简称>/验收报告.md`，把「我替你决定的」逐条列出来。报告不写，视为流程未完成。

| 门 | 批准人 | 文档怎么交给对方 | 对方怎么回 |

| G3 代码合入 | —— | **本模式不生效**（自动通过，仅报备：合入后交 `验收报告.md`） | —— |

> **这张表要按当前档位改，不能照抄模板**：
> `仅需求审批` ⇒ 把 G2 / G3 行标成「**本模式不生效**（自动通过，仅报备）」；
> `全自动` ⇒ 整表换成一句「无门禁，收尾交 `验收报告.md`」；
> `只在交付验收` ⇒ 只留最终验收一行。
> **留着不生效的门却不注明，等于告诉后来的人这里有三次批准 —— 实际一次都不会停。**

> **单人项目的 G1 特别说明**：PO 和 DEV 是同一人，技术上必然是「自己批自己」。所以不算违规，但**必须留痕**：

## 例外与约定

- 哪些阶段可以完全跳过：**没有整段可跳的**。INCEPTION（需求）/ CONSTRUCTION（设计+代码）都要走，只是 G2/G3 不停；
  OPERATIONS 只在部署类 CR 才产 `运维说明.md`。
- 哪些内容不需要走门禁（如纯文案）：
  - 纯问答、解释代码、读文件、查资料；
  - `开发文档/_汇总/` 的重建（生成物，不入库）；
  - `.gitignore` 里已排除的本地临时文件清理。
- 其他约定：
  - **`docs/` 下的历史资料只读**（`项目熟悉文档.md` / `Playground设计文档.md` / `搜索API接入待办.md`），
    新工作一律开 CR；`docs/待办.md` 降级为历史清单，不再当总表。
  - **接口契约变更必须回写** `api/docs/01.项目API文档.md`，否则算未完成。
  - **改了模型 YAML / 后端代码**：镜像内容烘焙，必须 `docker compose build llmops-api` 重建，否则「改完没生效」。
  - **密钥只在 `docker/.env`**，不写进仓库、不进 `开发文档/`、不进审计。
  - **前端构建产物 `ui/dist/`、数据目录 `docker/volumes/` 不入库**。
