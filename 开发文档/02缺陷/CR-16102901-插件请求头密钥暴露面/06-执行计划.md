# 06-执行计划

## 目标 / 非目标

- 目标：`api_tool_provider.headers` 从「明文落库 + 明文回显 + 明文回填」改为**密文存储 + 掩码回显 + 不改则保留**，
  并补上两处缺失的账号隔离。
- 非目标：不改插件的导入/OpenAPI 解析逻辑；不改 `api_tool` 表结构（复用 JSONB 列，不新增字段）；
  不动模型供应商、语音服务已有的密钥方案（保持同一范式）。

## 为什么不是「加一个新字段存密文」

`headers` 是 JSONB，直接在元素里加 `encrypted` 标记即可区分密文与历史明文：

```json
[{"key": "Authorization", "value": "gAAAAAB...", "encrypted": true}]
```

好处：零表结构变更、零 migration 依赖、旧备份恢复回来也能被 `decrypt_headers` 兼容（无标记按明文处理）。

1. 新增 `credentials.py`（加密/解密/掩码三件事收在一处，避免散落）。

## 风险与回退

- **主密钥依赖**：`credentials.py` 复用 `lib/secret.py` 的 Fernet（密钥由 `JWT_SECRET_KEY` 派生）。
  若 `JWT_SECRET_KEY` 变更，已存密钥全部解不开 → 表现为插件调用上游 401，日志有
  `API插件的请求头解密失败` 告警，需重新填写。这与模型供应商密钥的既有风险一致，不是本次引入的新风险。
- **前端未重建时的兼容**：旧前端会把 `****` 原样提交，`encrypt_headers` 同样识别为「不修改」，
  因此后端先上线不会打断使用（新前端只是把这层语义显式化）。
- **回退**：代码回退到本 CR 之前的提交即可；数据层无需回退（`decrypt_headers` 对无 `encrypted`
  标记的数据按明文处理，旧代码读密文会失效，所以**代码回退必须同时回退数据**）。
  回退 SQL 见 `07-决策记录.md`。

## 不做什么

- 不做密钥轮换/KMS 接入（超出本次范围，属另一条技术债）。
- 不改 `api_tool_provider` 表结构、不引入 alembic migration。
- 不为「Content-Type 这类非敏感头」单独豁免加密（统一加密，减少判断分支与漏判）。
