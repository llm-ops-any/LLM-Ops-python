# CR-16102808 决策记录

## D-01 用 subprocess 隔离，不用 Docker 容器 / WASM

| 方案 | 隔离强度 | 代价 | 结论 |
|---|---|---|---|
| **subprocess + setrlimit（选中）** | 中 | 零依赖、几十毫秒 | ✅ |
| 每节点起 Docker 容器 | 高 | 需挂 `docker.sock`，**等于把宿主机 root 交给 API 容器**；或引入独立调度器 | ❌ |
| WASM（Pyodide / wasmtime） | 高 | 需新依赖 + 大量标准库不可用（`hashlib`、`json` 勉强，第三方全废） | ❌ |
| `RestrictedPython` | 低 | 新依赖，绕过手法多，且不解决 CPU/内存 | ❌ |

- **理由**：本项目单机 Docker 部署，最大的现实威胁是「拿到 `.env` 里的数据库密码」和「拖垮服务」。
  挂 `docker.sock` 换来容器隔离，反而把风险放大一个量级 —— **攻击者能起容器就能挂宿主机根目录**。
- **被否**：Docker 容器方案。如果将来要多租户，应改成「独立的沙箱服务 + 网络调用」，而不是给 API 挂 socket。

## D-02 模块用**白名单**而不是黑名单

- **理由**：黑名单永远补不全（`os` 禁了还有 `posix`，`subprocess` 禁了还有 `pty`…）。
  白名单漏了顶多让用户报「模块不支持」，加一行即可；黑名单漏了是安全事故。
- **代价**：用户想用 `numpy` / `pandas` 会被拒。当前工作流只用 `json/hashlib/base64`，暂不放开。
- **后续**：如需放行，在 `SAFE_MODULES` 里加，不需要改架构。

## D-03 同时禁 `sys` 和 `getattr`

- **理由**：这两个是绕过限制的经典跳板 ——
  `sys.modules['os']` 直接拿到已加载的 os 模块；`getattr(__builtins__, 'eval')` 绕过名字检查。
- **代价**：极少见场景（动态取属性）会受限。当前无此需求。
- **被否**：禁 `sys` 会破坏 `print(sys.argv)` 之类调试代码 —— 但代码节点本来就不该依赖命令行参数。

## D-04 环境变量**清空式**传递，不做过滤

- **理由**：本项目 `docker-compose.yaml` 通过 `x-llmops-common-env` 注入了 30+ 变量，含数据库密码、JWT 密钥、各平台 Key。
  逐条拉黑容易漏（以后新增变量就漏了）；**只传白名单**才是默认安全。
- **代价**：用户代码里 `os.environ` 基本为空。这是**预期行为**。

## D-05 不设 `RLIMIT_NPROC`

- **理由**：容器内以 root 运行，**root 不受 NPROC 限制**，设了只是自欺欺人。
- **替代**：`start_new_session=True` + 超时后 `os.killpg(SIGKILL)`，把整个进程组一起收掉。
- **残留风险**：见 `04-风险.md` R-03。

## D-06 保留原有 5 类校验提示原文

- **理由**：这些提示用户已经见过，改了会造成「是不是改坏了」的误判。
- **做法**：原有 AST 校验逻辑**前移保留**，新增检查放在其后；错误文案逐字不变。

## D-07 超时 5 秒 / 内存 512MB / 禁写文件

| 项 | 值 | 为什么不是更严/更松 |
|---|---|---|
| CPU + wall timeout | 5s | 代码节点是数据加工，正常毫秒级；5 秒能覆盖大数据量处理，又不至于让用户等太久 |
| 内存 | 512MB | 处理几万条记录的字典列表够用；再大应该分页而不是塞内存 |
| 可写文件 | 0（禁写） | 现有节点不写盘；真要落文件应走上传统一管理，否则会在容器里堆垃圾 |
